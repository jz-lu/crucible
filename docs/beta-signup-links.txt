ONE-TIME LAUNCH SIGNUP — LOCAL CANDIDATE, 16 NOVEMBER 2026
=========================================================

Scope
-----
One shared link admits multiple people during this launch window. There is no
Invite people button or website API for creating/listing/closing campaigns.
The ordinary beta sign-in and recipient-bound invitations remain in place.
Each visitor enters an email, creates an account or signs in, then completes
mailbox verification. The link grants no reviewer or administrator permission.
Inspection and entering an email alone send no mail and grant no membership.

Issue at release, after the schema release gates pass
---------------------------------------------------
Use the existing trusted operator environment on the service host. Create the
launch link once, with an explicit timezone and a deadline no more than seven
days ahead. The actual deadline is chosen for this deployment; do not copy an
old sample date. The operator command is:

  python -m scripts.beta_access launch-link --expires-at <ISO-8601-deadline>

It outputs the secret URL only after committing the record. Share that URL with
the intended audience; do not put it in Git, CI logs or public documentation.
This campaign has one fixed identity per database. Repeating the exact command
recovers the original link and deadline. A different deadline is refused, even
after expiry or closure: it cannot create a second window or reopen this one.

  python -m scripts.beta_access launch-link

This reports the original deadline, status, successful joins and active URL.
After closure/expiry it returns no URL. To end the window early:

  python -m scripts.beta_access close-launch-link --reason <reason>

Closure is idempotent. Existing members keep access. New admissions, including
pending recipient invitations and provider signup flows, check the parent at
use time. A shared link cannot restore individually revoked access. A previously
admitted member opening it simply returns to their workspace.

Design and maintenance
----------------------
Two additive tables retain the window terms and recipient-invitation provenance.
The existing account, mailbox proof, membership, audit, CSRF/origin and quota
mechanisms do the remaining work. Server-side deadline checks need no cron,
extra worker or manual provider action. Keep the historical records after expiry;
do not remove tables that are still needed to explain admission history.

Tokens use domain-separated HMAC values; stored credentials are hashes. Repeated
claims for the same email reuse one recipient invitation without resetting its
expiry, resend or guess limits. Parent locks precede recipient locks. Mail is
sent outside database transactions. One mailbox never merges two identities.
Rotating the server secret prevents URL recovery; the command returns null.
It cannot open another campaign. Do not rotate the secret as a release step.
