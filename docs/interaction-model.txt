Crucible interaction model
25 October 2026

Use these rules when changing an existing journey or adding a new one. Different
workflows can need different freshness; explain the exception and test it. This
guide is the target contract. The follow-ups below identify known gaps rather
than claiming every existing page already satisfies every rule.

Shared rules

1. A URL identifies the destination and meaningful selection: scheme release,
   registered stage, view, note and pinned revision. Browser Back/Forward follow
   history; a labelled parent link (such as Leaderboard) goes to that destination.
   Within the same signed-in session, returning should preserve useful reading
   context. Keep scroll, disclosures and working drafts in view state, not URLs.
   Each workflow must explicitly define what refresh and deep links restore.

2. Previously authorized content can paint immediately within its bounded
   lifetime. Revalidate quietly without replacing an unchanged DOM, stealing
   focus or shifting surrounding controls. Pending is not empty; retained data
   for one query must never appear to answer another. Reserve neutral geometry
   when no content is available. Show errors with a usable retry, not an endless
   loading message. A failed refresh may retain a still-valid snapshot; expired
   or permission-rejected content must not masquerade as current authorized data.
   Show known layout and action invitations without waiting for unrelated data.
   An invitation is not confirmation of an empty result or permission to write.
   If a deliberate action needs a pending check, retain one scoped intent and
   show progress on that action; do not make the whole view disappear.

3. Every asynchronous completion belongs to its account/session, resource and
   selection, request generation and relevant read epoch. Check those owners
   before caching or painting. Account change/revocation clears private views
   and invalidates pending reads. A cache, prefetch or presentation hint never
   grants permission; the server remains authoritative.

4. Classify an operation by its effect, not just its HTTP method. Read-only
   specification validation must not cool unrelated browsing views. Known writes
   invalidate their dependent reads after a confirmed response. Keep conservative
   invalidation for unclassified writes until narrower dependencies are tested.
   Exceptions must name the exact operation and preserve transport/access guards.

5. A save/submission is complete only after its exact receipt is confirmed. An
   uncertain result retains its original idempotent payload for explicit retry;
   never automatically replay a write. Navigation must preserve a working draft
   or warn before discarding it. A draft or pending retry belongs to its account
   and exact source revision, not merely a similar-looking form.

6. Focus follows the user's action. Quiet updates preserve the focused control
   or a stable nearby fallback only when that view owns focus. They must not
   steal focus from a dialog or another workspace. Dialogs need explicit owners,
   return targets and navigation behavior. Keep status, empty, error and pending
   states distinct; neither a placeholder nor a stale snapshot enables an action.

Intentional differences

- Challenge issuance, round deadlines, beta admission and reviewer permissions
  require live server checks. Warm record summaries are for browsing only.
- Exact historical content can remain readable while mutable permissions or
  request status revalidate separately. A pinned note and a live review are not
  the same cache object. Preserve original release/revision and evidence identity.
- A complete notebook summary index permits local category/tag filtering and
  pagination. Typed search retains server matching; incomplete indexes, Trash
  and review queues use server reads. Do not approximate SQL Unicode semantics.
- Optional warming is finite, account-bound and subordinate to foreground work,
  visibility and Save-Data. Prepare metadata and selected detail intent, not all
  private bodies or generated challenges. Caches remain bounded and in memory.
- A labelled parent destination is not a promise to return to the previous page.
  Keep that distinction visible instead of replacing every parent link with Back.

Responsibility map

Navigation: web/app.js applyRoute/showWorkspace own the route and visible shell.
Notebook show/navigateView own notebook selections and its visualization scroll
reservation. Scheme URLs already preserve exact release, stage and view.

Session: web/bootstrap.js starts the initial session handoff. app.js api,
setSession/synchronizeSession own transport, access changes and revocation.
Notebook setAccount clears its private state. Periodic/visibility refresh does
not replace authorization checks on the server.

Reads: app.js owns shell/catalogue/detail/timing caches and the finite warming
queue. web/notebook/notebook.js owns summary/body/timeline caches, complete-index
queries and fallback pagination. These are separate domain owners following the
same identity/freshness rules, not a universal cache to consolidate by default.

Changes: app.js api owns CSRF, deadlines, errors and conservative invalidation.
The notebook API wrapper also invalidates its own reads; keep the two effect
classifications aligned. Submission, proposal and notebook save handlers own
their exact pending payloads and receipts. Shared transport must not take over
their workflow-specific uncertainty or permission decisions.

View state: notebook owns filters/pages/reader/editor; app.js owns People,
profiles, receipt dialogs and proposal review state. proposal-retractions.js owns
the retraction flow. Scope retained state to its account and exact resource.

First implementation and follow-ups

Implemented: format-only POST /api/protocol/proposals/validate preserves warm
Notes/Timeline and shell snapshots. Both wrappers keep conservative invalidation
for actual saves and other writes. Regressions cover warm -> validate -> cancel
-> return, actual-save invalidation, transport guards and account invalidation.

Implemented: the selected challenge's Ready card appears while its instance
status is checked. Get and Take on share one explicit start intent, scoped to
account, session, exact selection and round. The check opens an existing
instance or permits one issuance; denial, failure or an ownership change cancels
the intent. Cached instance tools still wait for fresh status. No instance is
created merely by painting the invitation or preparing metadata. Every stage
requires its own explicit request, even if another stage has been requested in
that hour. The server's optional active_round_id API guard remains compatible.

Implemented: Notes, Scheme map and Timeline share an inert public frame with
their admitted controller. Known headings, tabs and controls keep the same
geometry from access through asset/data reads. No placeholder invents private
titles, counts, graph points or permissions. The two challenge clocks share the
server-synchronized round state; a hidden or unknown round is not guessed.

Implemented: notebook pagination reserves list space while a page is pending
and preserves paging focus. The completed page uses its natural height, so a
short final page leaves no permanent blank area. Equal-height pages keep their
scroll position; a genuinely shorter document may naturally clamp it, without
an explicit scroll-to-top. A complete fresh summary index enables a bounded page
selector; incomplete indexes, search, Trash and review queues keep honest
Previous/Next controls without fake totals.

Implemented: Publish all confirms a fresh, complete bounded list of the author's
eligible exact revisions, independent of the current filters. Sequential requests
use the existing rate limit and review policy. Compact receipts avoid loading
note histories; default API responses stay compatible. Each retry retains its
exact idempotency key. Partial success is visible; uncertainty or throttling
pauses future sends. Session/navigation/dialog changes stop further writes,
without claiming that an in-flight request has been rolled back. No real notes
are published merely by deploying this feature.

Implemented: initial access and explicitly selected browsing reads may recover
once from a pre-response browser transport failure, within the original deadline.
Catalogue/release metadata, shared browsing reads and notebook reads opt in;
HTTP failures, body failures, raw downloads, session polling and writes are not
replayed. A failed speculative read is discarded rather than handed to a later
visible reader. Persistent failures retain a usable retry. Retired responses
cannot update their former view or rewind its clock; back/forward restoration
detaches interrupted reads before starting replacement work. Completed app
snapshots remain subject to their existing freshness and authorization bounds.

Implemented: recovery colors can refresh while the stage control owns focus,
without replacing controls or moving the selection/draft. Independent recovered
runs end at the actual stage positions; isolated recovered stages use small
centered marks. Unsolved gaps remain gray and record inheritance is unchanged.

Implemented: publication confirmation shows the exact saved note revision in a
compact selection card. Individual and bulk requests keep their confirmation and
retry semantics. An asynchronous card action remembers its originating button
before disabling it, so cancellation restores focus without scrolling.

Researcher profile edits follow the same ownership rules: the optional editor
is separate from score refreshes, retains a draft across in-app navigation, and
clears it on account/access changes. An uncertain save keeps its exact payload
and key; a conflict requires refreshed saved context and another explicit Save.
Cold profile frames show the known heading with quiet reserved space; optional
metadata and scores arrive together without displacing provisional score cards.
Metadata restores independently of score-DOM deduplication on a warm return.
Sign-in and agent controls remain session-owned during slow or failed reads.
See researcher-profiles.txt for the API and separate schema rollout boundary.

Implemented: publication-request lists use an opt-in compact server projection
and the notebook's existing bounded, session-owned summary cache. Returning to
an exact cursor paints its still-valid rows immediately and refreshes quietly;
unchanged results retain row DOM, expansion and focus. Concurrent reads for that
exact query share one request. This does not cache review forms or authorize a
decision: opening an exact revision still fetches current detail, and every
decision is checked by the server. Permission denial, session changes and
confirmed writes invalidate retained summaries. Transient refresh failures keep
a valid snapshot with an explicit retry without renewing its expiry. Summary
queries batch metadata and omit full note bodies and proposal specifications;
the existing full API response remains available to callers that request it.

Implemented: admitted reviewers also prepare the first two publication-summary
pages as separate jobs in the existing idle warmup queue. Each page counts toward
its normal job/byte budget; foreground work, open dialogs, hidden tabs and
Save-Data defer optional reads. Visible publication paging prepares only its next
page after the current page settles, never the rest of the queue recursively.
Brief overlapping reads defer this one-page preparation for at most ten seconds;
leaving the page cancels it, and failed network reads are not retried automatically.
Preparation uses the same bounded, five-minute, account/session-owned summary
cache and exact-cursor single-flight reads. A completed preparation can be
consumed once within ten seconds without a redundant refresh; consuming it does
not renew its original expiry. Later visits paint valid summaries while quietly
refreshing them. Failed preparation is discarded, and permission denial retires
pending reads as well as cached summaries. No body, review form or decision is
prepared, and the server still validates every review action.

Next, in priority order:

1. Review -> evidence -> return: protect unsent review findings/checks. Key any
   retained draft by account, proposal revision and content hash; changed evidence
   must not silently inherit approval checks. Recheck permission before enabling
   actions. Existing uncertain-write retries are a separate state to preserve.
2. Notebook reader -> return -> refresh: make filter/tag/search restoration an
   explicit URL contract. Current bare #notebook retains more state in an active
   controller than a fresh load can recover. Keep opaque pagination cursors
   transient; don't fetch an arbitrary number of pages to reconstruct a URL.
3. Reproduce People Load more -> profile -> Back, and receipt dialog -> browser
   Back. Decide how loaded ranges and read-dialog ownership survive navigation
   before changing them; don't discard editors to solve a read-dialog problem.

Review evidence

Each UI change should name the rule, affected journeys and remaining exceptions.
Use the existing standalone JavaScript and disposable Chromium suites to cover
slow/out-of-order reads, warm return, save/uncertain retry, focus and account
changes as appropriate. Check desktop/mobile geometry where layout changes.
First paint must be styled before access resolves; post-admission lazy styles
may be prepared without becoming a dependency of that first paint. Tests should
verify this distinction rather than race legitimate background work.

Local request counts establish removed waits, not universal hosted latency.
Verify the exact released source before attributing a hosted result to a change.
No framework migration or broad rewrite is implied by this interaction model.

Implemented 29 October 2026: resource graphs participate in the existing finite
scheme-preparation jobs. Each scheme job overlaps its release description and
compact resource projection and charges both response sizes. The scheduler keeps
its 24-job and eight-current-release bounds and checks its 4 MiB budget between
jobs; the final job can exceed that byte threshold. Hover/focus intent and
selected overview deep links start the independent resource read without waiting
for the release description. Save-Data, hidden documents, foreground requests
and open dialogs retain their existing optional-work guards. Preparation never
issues a challenge or starts a measurement job.

The opt-in resource projection=charts endpoint returns exact stored graph values,
lifecycle/publication identities and deduplicated measurement context. The full
API response and downloadable evidence remain unchanged. Contradictory context
for one comparison-profile identity is rejected rather than silently merged.
Chart caches remain in memory only: 60 seconds fresh, five minutes usable,
at most 24 reports and 8 MiB of serialized report data. Quiet refresh retains a
usable curve and unchanged controls. A foreground reader joins an in-flight
prefetch and receives its completion; failed unused prefetches do not poison a
later visit. A retired document detaches pending listeners before restoration.

Confirmed note creation/import/revision/publication requests or reviews, profile
edits, attack-method submissions and challenge issuance/submission invalidate
their normal browsing summaries without discarding independent measurement
reports. The exception lists exact existing paths and methods; unknown writes
still clear the resource cache. Catalogue identity changes, account/session or
capability changes, and denied access retain unconditional invalidation. Cached
measurements do not authorize any action. A hard reload still requires a fresh
session and authorized reads; background preparation reduces subsequent waits.
