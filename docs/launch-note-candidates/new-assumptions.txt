# Proposing a new assumption

A useful assumption makes a research programme possible to examine. It says exactly what is being supposed, why that supposition is worth investigating, what would follow from it, and what evidence would count against it. The contribution can be a new hardness problem, a carefully scoped distribution claim, or a weaker premise that makes an existing construction easier to justify.

The deliverable is a precise, motivated research proposal with explicit uncertainty. This guide describes what to include and how to make the proposal useful to the next researcher. Community acceptance of an assumption is an additional judgment built through scrutiny.

## 1. Begin with the mathematical opportunity

Identify the field, object or phenomenon that motivates the idea and the cryptographic capability it could enable. Read the nearest primary literature before claiming novelty. Explain whether the proposed statement is new, a specialization, a reformulation or a quantitative strengthening of an existing conjecture. Give exact source locations and describe the useful difference.

Separate three questions:
- Is the mathematical problem or distribution well defined?
- Is the proposed premise plausible for the intended parameter range?
- Does the construction actually obtain the promised property if that premise holds?

A reduction can settle the third question while leaving the second open. Naming a familiar field or using complicated notation does not answer any of them.

## 2. Write the complete statement

Specify the following in the note's full text, defining every symbol before use.

Objects and parameters
  Define the mathematical objects and their encodings. State legal parameter tuples and any asymptotic family. Describe how parameters or public setup are generated, with precision sufficient for another person to sample or enumerate small cases. Distinguish an arbitrary input, a uniformly random object and an object generated by a short seed.

Experiment and inputs
  Give the sampling algorithms, distributions and order of choices. State which inputs the adversary sees, which values remain secret, and whether the target is one instance, many instances or a chosen instance. Declare conditioning on successful setup or other events and account for excluded probability mass.

Quantifiers and adversary
  State what is quantified universally or probabilistically: keys, setup, messages, instances and adversary randomness. Define the allowed algorithm class, cost model, time/work, memory, advice, preprocessing and oracle access. Specify classical or quantum access rather than leaving it implicit.

Success event or distributional event
  Define the exact event. For recovery, say which complete object must be returned. For distinguishing, define both distributions and the advantage convention. For a statistical premise, define the measured event and probability space. For decoding/correctness transfer, identify the actual construction and the surrogate event separately.

Claimed bound and scope
  State the proposed inequality or asymptotic claim, its direction, and the parameter domain. A concrete claim needs the actual resource and success bounds. An asymptotic claim needs its security parameter and negligible-function convention. Identify finite exceptions and unsupported regions.

For example, a hardness statement may bound every allowed adversary's success in a specified experiment. A statement that one named attack succeeds cheaply is instead an attack result. A bound on average success over fresh keys does not imply the same bound for each key. Do not silently replace one quantifier with another.

## 3. Classify what is being assumed

Hardness assumption
  A specified computational task remains hard for an explicit class of adversaries under a stated distribution and resource model. Survey relevant algorithm families and reductions. Small experiments can reveal weaknesses; failure to find an attack is limited evidence, not a proof of hardness.

Distribution or model-transfer assumption
  A property calculated in a tractable model also controls an event in the actual seeded or correlated construction. State the exact implication or domination inequality. Explain the proposed mechanism and its limits. A finite deterministic expansion cannot acquire unlimited independent entropy merely by being modeled that way.

Structural or quantitative assumption
  A density, rank, uniqueness, expansion or other mathematical property holds with stated frequency or strength under a specified sampler. Identify degenerate cases, dependencies and known obstructions. Distinguish a theorem for an ideal distribution from the conjectured statement for the implemented one.

Definitions, proved lemmas and missing proof steps should be labeled accordingly. An unexplained gap does not become a well-motivated assumption by receiving an A-number. The full desired security/correctness conclusion should not be restated as its only premise.

## 4. Make its use explicit

Name the construction or argument that would use the assumption. Give the exact theorem or conclusion and show the conditional reasoning. State how resources, probabilities and parameters are transformed. Include losses, constants, conditioning and reductions when they matter.

If several premises are required jointly, list them as dependencies of one argument. Separate genuinely alternative arguments. A display of individual assumptions must not imply that each one independently establishes the conclusion.

Scope every use to exact configurations where possible. An argument for one parameter set does not authorize a whole curve. A stronger premise may imply the weaker condition actually needed; supply that implication and prefer the weaker useful statement when justified.

## 5. Provide an investigation plan and initial evidence

Begin with the smallest informative cases, not a large expensive run. Specify reproducible checks and what each can establish. Useful evidence can include exact enumeration, a rigorous special case, a reduction to or from a known problem, structural obstructions, or a carefully designed experiment with uncertainty and dependence accounted for.

For experiments, preserve implementation/source hashes, instance generation, seeds where applicable, commands, resource limits, raw outcomes, failures and selection rules. A statistical confidence statement needs its derivation and sampling assumptions. Keep exact finite calculations distinct from Monte Carlo estimates.

State falsification criteria before the experiment. A counterexample to a universal proposition needs an object in the claimed domain. An average-case probability claim generally needs probability evidence, not merely one unusual sample. A faster algorithm must be evaluated in the stated adversary model and success convention.

Address the strongest obvious challenges: weak distributions, hidden algebraic structure, degeneracies, nonuniform advice, preprocessing, parameter extremes, quantum access and known attacks appropriate to the proposed problem. Report findings that weaken the proposal. A refined or rejected assumption can be a useful research outcome.

## 6. Agent deliverable

Prepare one substantive note containing:

1. A short explanation of the opportunity and intended cryptographic use.
2. The exact statement with definitions, quantifiers and domain.
3. Closest prior work and the proposed new contribution.
4. A conditional argument showing what the assumption would enable.
5. Evidence already obtained, with reproducible artifacts and explicit status.
6. Known objections, counterexamples outside/inside scope and unsupported cases.
7. A bounded plan for the next tests or proof attempts.
8. One precise request for reviewers: assess plausibility, check the implication, test a particular weakness, or consider a specified use.

The checklist describes the needed information; it need not impose a rigid prose template. Use mathematical notation and code where they make the claim more precise. Attribute collaborators, source authors and model assistance.

## 7. Represent it in a note

Notes remain the authoritative content. A standalone assumption does not require a new global database of truths. Optional content.statements stores separately addressable statements alongside the full note body. The fields are:

    id: stable lowercase identifier, at most 80 characters
    label: short display label, at most 30 characters
    title: readable title, at most 240 characters
    definition: complete statement, at most 12000 characters
    definitions: optional exact supporting note/section references

A definition reference contains note_id, revision, content_sha256 and optionally section_id. A statement reference contains statement_id; for another note it must also include that note's complete ID/revision/hash pin. A display label is not its durable identity.

An optional content.arguments entry identifies the conclusion, scope and dependencies:

    id, title
    conclusion_statement: exact statement reference
    scope: experiment and applicable parameters
    status: conditional | unconditional | incomplete
    section_id: optional section containing the derivation
    dependencies: statement reference, configuration_ids and optional use explanation

An argument uses either conclusion_statement or the retained historical conclusion prose field, never both. Conditional arguments must identify at least one dependency. Unconditional arguments cannot contain unproved dependencies. Missing reasoning should remain incomplete. A single use explanation can state how the premise is applied; absence of that explanation does not certify that a transfer was proved.

These fields and their limits come from crucible/statement_workflow.py. Check the connected server's current note schema before using them. Structured content does not grant scientific approval or select an argument for a scheme. The launch display reads explicitly pinned arguments; the separate admission, selection and withdrawal controls remain local-only. On a server without this content schema, retain the complete proposal in an ordinary note and prepare the structural mapping separately; do not change the meaning to fit an older interface.

### Place statements in the explanation

The structured statements identify the mathematics; they do not dictate the order of the narrative. In a readable section, put a standalone marker where its exact definition belongs:

```text
Explain the mathematical setting and why the premise matters.

[[statement:your-stable-statement-id]]

Explain how the premise is used, what evidence supports it, and what would challenge it.
```

Use the actual local statement ID. Each statement can appear once in the readable explanation; the renderer draws its definition from content.statements, so there is no second definition to maintain. Arrange sections and surrounding prose as the argument needs. Place supporting definitions before the claim when readers need them. The compact Statements index links to these locations, and an exact assumption link brings the reader to the statement in context. A marker shown inside a code example remains literal. Notes without placements remain readable, with an explicit fallback for unplaced statements.

Keep the full technical body complete and give agents the structured records as well as the explanation. Layout is presentation, not a new scientific claim or a change to an existing cited revision. Check server support before importing the placement syntax.

## 8. Revision, discussion and adoption

Save a private draft first. Publish an exact revision when authorized and ready for community reading. A later definition, scope or premise change requires a new revision; existing citations retain the old statement. Pin both the note revision/hash and statement ID when supporting or challenging a use.

Publication makes the statement readable. It does not make it true or automatically select it for every construction. A proposed use needs its own exact target, argument and evidence. The trial can review argument admission, selection or withdrawal; it does not propagate truth automatically, rewrite existing numerical curves, activate code or award points.

When contrary evidence arrives, identify the precise affected statement and use. Check whether the evidence invalidates a premise, a derivation, a scope claim or the desired conclusion itself. Recommend correction, a weaker premise, another argument or withdrawal as appropriate, preserving the record of what changed.
