PUBLICATION SCREENING INPUT ADMISSION — 2026-11-06

Problem and change
------------------
Four previously submitted exact revisions stopped before provider generation.
They contained 105,051–273,509 canonical bytes, 158–558 nodes and depth 3–6.
All hit input_budget_exceeded, not content-size or structure limits. The old
128,000-unit admission test counted serialized UTF-8 bytes plus framing, not
model tokens. JSON escaping and the field graph increased those estimates.
The diagnostic retained numeric measurements only, not private note content.

Small inputs still take one generation request. When the conservative estimate
is above budget, the worker asks the provider to count the exact supported
request inputs, then permits generation only at <=128,000 input tokens. The
same complete content, instructions, model settings and output schema are used.
Truncation is explicitly disabled. Counting cannot grant publication authority:
author, exact revision, pending request, policy and lease are rechecked before
sending generation, and again before committing any publication.

The v3 prompt, output schema and input-v1 bytes/field IDs are unchanged. The
policy snapshot pins the new admission method; existing jobs are not silently
retargeted. Historical evidence reconstructs its versioned input independently
of a later prompt size or admission budget. No schema migration is needed.

The arbitrary 4,096-node cutoff becomes the five-digit field-ID ceiling (99,999).
The existing 384 KiB source limit and depth 32 guard remain. Notebook storage rules
are unchanged. A local worst-case synthetic graph with 99,999 nodes used approximately 114 MB
process peak RSS and constructed in 0.237 seconds on this Mac; this is not a hosted
benchmark. A native release check remains required. The field graph itself
still consumes tokens, so this does not claim to eliminate all representation
overhead or support arbitrary inline datasets.

Bounds and verification
-----------------------
One existing global lease/reservation covers count plus generation. Both calls
share 45 seconds; each attempt makes at most one count and one generation request.
Count failures go to human attention without repeated blind calls. Ambiguous
generation still retains its reserved charge. Validated actual generation costs
are preserved even if a provider unexpectedly exceeds the reserved cap; such a
result cannot publish. Publication remains exact-revision and idempotent.

Focused regressions cover complete round trips, metadata beyond 4,096 nodes,
count-request identity, malformed/oversized counts, no implicit truncation,
mid-count cancellation/revocation/human decisions/policy changes/expiry, known
overspend, historical findings and bounded operator repair. Header-centering
has 11 focused desktop/mobile Chromium checks. Full CI and native image release
checks are separately recorded in GitHub, not implied by this local report.

Repair of the four earlier preflight failures
--------------------------------------------
publication_screening_retry is a separate trusted-host operator action. Preview
requires an explicit list of at most 25 publication IDs; applying requires the
same fresh SHA-bound plan, current automatic policy and active access admin.
Only an exact still-pending automatic-mode request with a single zero-generation
preflight attempt is eligible. No model flag, shadow-only consent, ambiguous
usage, human decision, cancellation, withdrawn/deleted note or inactive author
can enter repair. Old jobs/attempts/costs remain; a new policy creates a new job
and audit event atomically. Replaying the plan never creates a second job.
There is no participant API, startup scan or automatic requeue of terminal jobs.
