CRUCIBLE — PROTOCOL REVIEW AND ADMISSION

This first workflow accepts specifications and records manual review. It never
executes uploaded algorithms, downloads an implementation URL, or automatically
adds an approved proposal to the live challenge registry.

Enforcement reviewed on 16 October 2026. Sections below distinguish implemented
workflow checks from the scientific judgments a reviewer must make. They do not
claim automated certification. The detailed requirements crosswalk and proposed
extensions are in scheme-reviews/admission-and-coverage-challenge.txt, section 8;
the immediate catalogue trial recommendation is in section 9. The current common
correctness goal is a claimed honest disagreement probability at most 2^-128;
conditional claims and their premises are reviewed under correctness-policy-v1.txt.
See proposal-guide.txt for a concise entry point for people and agents.

1. Describe the scheme

Use crucible-kem-spec-v1. The website supplies an annotated template, JSON Schema,
and descriptions of each exact registered DH/RSA release. Specify algorithms,
configuration/stage mappings, random distributions, encodings, correctness, security
claims, and what setup is reused. Shared public parameters are legitimate when
they are part of the specified construction. DH group reuse is retained.

Specification-only proposals are allowed. The team can assess the pseudocode and
claim, assumptions and supporting reasoning first, then create or inspect a reference implementation.
Final approval still requires its exact SHA-256 fingerprint and the implementation
review checks; there is no new partial-approval status. Publish reference timings
only after implementation review, separately from correctness/security claims.
Format validation checks structural completeness and consistency, not mathematical
truth or executable conformance. Intake never executes contributed code.

2. Submit and preserve a revision

The author explicitly submits the checked document through a browser session or
an agent connection with proposal-write permission. The CLI supports draft,
format validation, submission, feedback and revision; the website provides its
copyable agent handoff alongside manual upload. It is visible to its author and
configured reviewers. Agent proposal-read permission is owner-only, including
for reviewer accounts. Each revision is immutable and has a stable
content hash. Retries with the same request identifier return the same receipt.
Revising requires the current revision and hash; a new revision returns to review
and cannot inherit an earlier approval. Earlier revisions and decisions remain
part of the record. These submissions do not affect numerical leaderboards.

3. Review the exact artifact

A configured reviewer, different from the author account, may request changes or
approve the current revision. Approval requires all seven review checks, notes,
supporting evidence, and the implementation hash from the specification:

- Specification completeness: independently implementable pseudocode for all four
  algorithms, exact sampling/conditioning, encodings including private-key state,
  arithmetic, helpers, retries/termination, stage/configuration mapping, reusable
  setup, KDF framing/domains and every invalid-input branch. Pin standard/theorem
  versions and sections where operations are incorporated by reference; identify
  adaptations. Require an explicit security notion, scoped guarantee and its
  assumptions, with unknown evidence labelled; no invented numerical bit estimate
  is required for a new asymptotic claim. When security uses a correctness bound,
  record that dependency and any required failure threshold explicitly. No
  particular programming language or
  proof assistant is required.
- Correctness: review a precise claimed guarantee (perfect agreement or an explicit
  statistical failure bound at most 2^-128), probability scope, parameter coverage
  and underlying assumptions. correctness.justification records statement, conditions, coverage
  and reasoning. Model-based and conjectural claims are eligible when the premises
  and unproved steps are explicit and independently motivated. Unknown correctness
  and weaker bounds are draft-only. For new approval/admission, statistical claims
  require a conservative integer failure_bound_exponent >=128, consistent with the
  declared bound and its scope; perfect claims state bound "0" and omit the exponent.
  policy_id is optional. This is a required claimed goal, not proof certification.
  A reviewer can assess the claim without proving every assumption. Identify
  dependencies and what could support or refute them; never turn a conjecture
  into a verified badge. Assumptions must identify independently assessable
  properties, not merely assume the target conclusion. Empirical tests cannot
  establish a negligible failure rate. Report generation aborts and conditioning separately. See
  correctness-policy-v1.txt for the full claims-and-assumptions policy and the
  difference between refuting the actual target and undermining its justification.
- Stage design: admissible configurations distinct from the versioned default
  progression; exact stage-to-configuration mapping and stable identities; faithful
  natural scaling, real cost tradeoffs, the scheme's declared correctness envelope,
  reference endpoint evidence and limitations, and useful intermediate settings.
  Assess changes in several parameters together and whether a denser route adds
  genuine useful choices. A multiple-of-ten/five default count is a presentation
  preference only; scientific validity and useful settings take priority. The
  structured tier_design plan must be present in this exact revision.
- Parameter selection: a declared objective, fixed construction/correctness and
  interoperability constraints, pinned security/cost model, candidate search
  domain, comparison evidence, and tradeoffs/uncertainty for every target. The
  tier_design.parameter_selection plan must be present in this exact revision.
- Implementation conformance: inspect the pinned source and compare behavior to
  the specification. Record deterministic known-answer and honest round-trip tests.
- Input and resource safety: malformed inputs, public/private data separation,
  output bounds, generation time, isolation requirements, and failure behavior.
- Reproduction: record exact commands, source/dependency versions, test inputs,
  results, and any limitations. Include reproducible evidence, not just a checkmark.

These are recorded manual assessments. Approval does not certify security or
prove that an implementation is free of defects. The API rejects stale decisions,
unconfigured self-review, incomplete approval checks, missing evidence, unknown
correctness, absent claim reasoning/private-key representation, or
mismatched implementation hashes. Historical documents remain readable and keep
their canonical hashes. These new fields are optional for drafts, but an old
approval lacking them cannot pass a new admission check; it needs a new revision
and review. Existing built-ins are not retroactively marked as rigorously reviewed.

The statistical failure bound is inert text; its numeric validity, probability
scope, proof versus heuristic status, and coverage of every admitted profile
remain substantive review duties. Evidence strings and completed checks do not
establish that tests ran or a theorem is true. Distinct reviewer and author
accounts are enforced outside the explicit development exception below; separate people or freedom from conflicts are not proven.
Agent credentials currently have no proposal-review authority. Automation may
prepare and reproduce evidence, but must not impersonate a human signoff.

Configuration and stage review — 2026-10-16

A configuration is an exact parameter set or a fully specified reviewed generation
rule over a declared domain. Give it a stable identity. The default progression is
an ordered selection of reviewed configurations; a stage is its local ordinal.
A challenge instance is one random sample at that configuration. Alternative
settings can belong to the same scheme without a separate catalogue entry.
Every admitted setting, including those outside the default route, needs validity,
correctness and implementation coverage. A prose generation rule is never executed
by intake, and a proposed domain does not itself enable live challenges.

Version configurations, default progression mappings and security evidence
separately in the proposal and integration record. Inserting an intermediate stage
must not change the meaning of old configuration IDs or recovery receipts. Current
v1 intake still uses tier_meaning, supported_tiers and tier_design as wire names;
registered manifests retain instance_size. supported_tiers and instance_size keep
their legacy numeric configuration-selector meaning, including off-route settings;
map displayed stages separately. These names and canonical hashes remain unchanged. There is no independent progression-edit API
yet. See ladder-principles.txt for the accepted design direction and limits.

The specification's parameter mapping must explain what grows, what costs
change, and why the selected parameters are reasonable within the construction.
Use the same declared correctness upper bound throughout a versioned progression;
keep resource/generation aborts separately visible. Changing spare decoding
margin is not itself a practical cost while the guarantee remains unchanged.
Review generic message/seed enumeration as well as the named hard problem.
Preserve the family, full declared sampling distributions, transform and game;
justify coordinated parameter changes. Do not manufacture easy settings using
leaked information, specially easy keys or selective resampling. Naturally small
spaces can enable generic attacks; disclose them and avoid extrapolating a small
recovery to the reference endpoint. Retain a published/approved reference endpoint
where applicable; a new construction must justify its own reference setting.

Zero failure is not required. Every admitted configuration must satisfy the same
reviewed strong correctness envelope. Disclose stronger per-configuration bounds
and material variation; equal actual probabilities are not required. A proof of
a generation rule must cover its entire admitted domain. This remains manual
review, not automatic verification of a bound.

Prefer a default-stage count in multiples of ten, or five when more natural,
provided the resulting path is useful. This is not a review gate: do not change
parameters, duplicate configurations or discard a reference endpoint to fit a
count. Retain reviewed off-route configurations and their credit. Do not select
inefficient profiles solely to draw a convenient security curve.
Meaningful adjacent profiles may have the same byte size, and not every cost
must rise at every step. State the scope of any parameter optimization and
explicit exceptions such as a published endpoint. Communication graphs show
the actual registered encoding; benchmark timings require measured evidence.

The template and schema provide a bounded tier_design section with seven progression fields:
parameter_progression, cost_tradeoff, fixed_correctness, endpoint_status,
endpoint_target, endpoint_evidence, and intermediate_steps, plus the nested
parameter_selection plan below. Endpoint status may
be supported-estimate, provisional, or unestimated; none grants a security claim.
Drafts may omit the section. When supplied, every field must be complete. New
approval and admission require it plus explicit stage-design and parameter-selection
review checks.
This is a substantive manual assessment, not a theorem checked by the validator.
Existing proposals and approvals remain readable with unchanged canonical bytes
and hashes when the section is absent. They are not silently grandfathered into
future admission: a missing plan or check requires a new revision and review.
The current route audit is in stage-progressions.txt; earlier assessment is in
ladder-design-review.txt. These records disclose limitations rather than certify
that every built-in progression already meets the new scientific guidance. Changes to
parameter distributions or wire formats require distinct registered releases;
old challenges and results retain their original contracts and attribution.

Parameter selection review — 2026-10-16

At each stated security target, choose efficient parameters naturally available
within the proposed construction. Increasing cost is not a goal in itself. Do
not weaken one parameter while making another unnecessarily more expensive merely
to draw a smooth ladder. A curve of equal security targets is only meaningful
under a stated adversary, attack model and cost convention.

The nested tier_design.parameter_selection object has six bounded text fields:

- objective: the actual cost to minimize, including units, workload and weighting,
  or a Pareto tradeoff when communication, memory and computation compete.
- constraints: the construction, security game, common correctness envelope and
  interoperability or implementation constraints held fixed. No artificial wire
  padding or restricted seed/message entropy solely to manufacture stages. A
  naturally shorter secret parameter may be justified with its attack analysis;
  it is not prohibited merely because a larger secret space exists.
- security_model: pinned estimators, source versions, assumptions and treatment
  of setup, reusable precomputation, classical and quantum attackers. State which
  attacks were compared and use compatible cost units; do not equate operations
  from unrelated models. Missing calibrated evidence must remain explicit.
- search_domain: candidate ranges, admissibility filters, construction choices,
  actual search coverage and excluded alternatives. Record reproducible commands,
  data and versions in the evidence or pinned reference artifact.
- comparison_evidence: compare the chosen point with cheaper admissible candidates
  at each target, or give a mathematical dominance argument. Prefer a point for
  which no inspected candidate meets the same target at strictly better stated
  costs. This establishes only a conditional result in the inspected domain; a
  short list or heuristic search does not prove a global optimum.
- tradeoffs_and_uncertainty: competing objectives, estimator uncertainty,
  unexplored alternatives and explicit exceptions such as a published endpoint.
  An established anchor can aid interpretation without being cost-optimal.

When calibrated attack estimates are unavailable, do not label the selection an
optimum at a known security level. Give justified structural/cost comparisons and
a provisional or unestimated endpoint; say which review remains outstanding.
A reviewer must check each configuration or covered family's selection argument,
rather than only the endpoint. Benchmarks are optional until available, but an unmeasured runtime must
not be advertised as a measured improvement. Natural gaps are preferable to
artificially inefficient intermediates. Keep the correctness upper bound fixed.

The review records three separate domains: mathematical admissibility, support
by the pinned executable, and coverage of the correctness and attack models.
Parameter generality in a specification does not establish decoder generality.
Keep candidate tables, exclusion reasons, exact model options, commands and
source pins with the evidence. An optimizer's best result under an incomplete
model is a candidate, not a security guarantee or an admission decision. In
particular, report missing structural attacks separately from generic decoding
estimates, and distinguish planted-instance and random-instance assumptions.
Plan replacement release/profile identities and any scoring treatment before
activation; existing recoveries and measurement publications keep their identities.

The validator checks bounded fields and labels, never executes a search or
compares arbitrary formulas. Approval and admission enforce presence of the plan
and its manual check; truth and coverage remain reviewer responsibilities.
Older plans without parameter_selection keep their exact canonical bytes and
hashes, including when the optional new object is null. Historical decisions
remain readable and exact retries remain inert. A new approval/admission requires
a completed revision and new review; there is no silent grandfathering.

Development self-review

For local workflow testing only, an operator can export
CRUCIBLE_ALLOW_SELF_REVIEW=true when starting a development server. This defaults
to false, accepts only exact true/false, and refuses startup in production when
true. It does not grant reviewer status: only configured account UUIDs can use
it. Browser session, origin and CSRF checks still apply; agent credentials still
cannot review. Own pending proposals appear in that reviewer's queue.

The form and immutable review history explicitly label these decisions as
"Development self-review". The server, not the client, records
checks.test_only_self_review=true for approvals and change requests. All normal
approval evidence and completeness requirements still apply. Turning the flag
off leaves the history readable. Such an approval can test the revision workflow
but cannot pass independent admission or earn scheme contribution credit. Submit
a new revision for a separate reviewer when ready for actual admission. This
exception does not change the trust boundary for executing code or activation.

4. Integrate reviewed code explicitly

A maintainer integrates the reviewed implementation and its tests in the trusted
repository. Source files for existing releases remain frozen. New executable code
is never imported from a proposal URL. Register the new adapter in ADAPTERS before
enabling it in CURRENT; review any dependencies and adapter integration separately.

Run the read-only binding check:

  .venv/bin/python -m crucible.manage check-proposal \
    --proposal-id PROPOSAL_UUID --scheme-id SCHEME_ID --version RELEASE

It requires the latest approved revision, independent review and evidence,
matching specification hashes, the exact registered source fingerprint, matching
release/stage coverage, unique consistent profile IDs, and valid per-profile
shared-secret lengths (matching the fixed length where declared). It also requires
the reviewed stage-design and parameter-selection plans/checks and consistent
correctness declarations. A
perfect ladder must declare zero failure at every profile. For a statistical
ladder, statistical profiles must repeat the exact reviewed common failure-bound
text; stronger perfect-zero profiles are allowed, as in Frodo's first profile.
Use the common bound in the declaration and explain tighter profile results in
the evidence. Expressions are never evaluated or compared mathematically: even
equivalent spellings must be aligned, and proof coverage remains human review.
It reads only trusted registered code; it does not generate challenges, run
submitted attacks, fetch URLs, grant approval, or change CURRENT.

Passing this check is one integration gate. It cannot verify that prose describes
the implementation correctly or that the test evidence is truthful. The trusted
code change enabling CURRENT is the final manual activation step, after review
of integration tests, failure handling, resource limits, and source provenance.
Keep the check report with that change. Changed code needs a new reviewed artifact.

CURRENT is a trusted manual code gate: runtime issuance does not consult the
proposal approval ledger. The binding check is therefore not an automatic or
unbypassable activation control. The activating maintainer must verify the report
and record the decision for the exact artifact/profile set. Admission credit and
recovery-scoring enrollment are separate explicit decisions.

The source fingerprint covers the registered adapter source file. Adapters whose
manifests declare artifact_sha256 also need the reviewed full implementation
closure hash and an inspectable, verified artifact manifest; the admission check
binds that closure. Integration review must ensure it actually covers every
behavior-affecting source, native binary, dependency and build recipe. A wrapper
hash or an incomplete closure cannot establish that scope by itself.

The live service currently pauses a profile on any agreement mismatch and does
not implement a general statistical-failure ledger or issuance policy. Keep this
conservative behavior for existing DH6/RSA3; do not extend it to a statistical KEM
by assumption. Such a candidate needs an explicit failure/abort/distribution
policy before activation, including how legitimate mathematical disagreement is
distinguished from bugs. No hidden resampling or substitution of Decaps' key is
allowed. See correctness-policy-v0.txt and crosswalk requirements R1–R8.

5. Configure reviewers explicitly

Local administration resolves an existing handle to its stable account UUID:

  .venv/bin/python -m crucible.manage grant-reviewer --handle HANDLE
  .venv/bin/python -m crucible.manage revoke-reviewer --handle HANDLE

Restart the local server after changing access. The private data directory stores
reviewers.json with restricted permissions; it must not be committed. The file
contains stable user IDs, never passwords or session credentials. An unregistered
name cannot reserve reviewer rights for whoever signs up later.
Local macOS/Linux commands lock the read-modify-write operation and reload the
latest policy under that lock, so concurrent grants and revocations are preserved.

Production uses CRUCIBLE_REVIEWER_IDS explicitly. An environment setting overrides
local configuration. No account is made a reviewer merely for registering, and
existing challenge records are not retroactively marked reviewed by this workflow.

Reference guidance

NIST's submission guidance distinguishes specifications, implementation, known-
answer tests, and security analysis. Crucible's initial intake is intentionally
smaller and makes no claim of NIST compliance or endorsement:
https://csrc.nist.gov/Projects/Post-Quantum-Cryptography/Post-Quantum-Cryptography-Standardization/Submission-Requirements/Algo-Specs-%28PQC%29

Stage counts and scoring

Different schemes can have different numbers of stages. All useful natural
configurations may appear in the default progression. Multiples of ten, or five,
are a soft presentation preference; the scientific review does not require them.
The existing ordinal point formula is provisional. Existing configuration credit
stays fixed when a route is curated or renumbered. A future scoring revision must
avoid awarding more for the same recovery merely because a route gained steps. Review or admission alone
does not automatically change recovery-scoring enrollment.
