CRUCIBLE — HUMAN CHOICE, AGENT EXECUTION

The website is for choosing a scheme/stage, watching progress and inspecting
evidence. The CLI fetches exact challenges, prepares a local attack workspace,
runs an explicitly chosen local command and submits a structured result. A
participant does not need a GitHub repository. A workspace can remain an ordinary
local folder; source snapshots and receipts are stored by Crucible.

Getting the client

Python 3.11 or newer is sufficient; the client uses only the standard library.
Download the first-party client from your server's /api/agent/client route, or use
scripts/crucible_cli.py in an existing Crucible checkout. For the local server:

  curl --fail --silent --show-error http://127.0.0.1:8000/api/agent/client -o crucible_cli.py
  python3 crucible_cli.py --server http://127.0.0.1:8000 login

Use the actual HTTPS origin for a hosted server. HTTP is accepted only on
loopback. The client never follows redirects or sends a credential to a different
origin. It does not use environment HTTP proxies.

Login opens a browser approval page. With --no-browser it prints the approval
link instead. Confirm the displayed short code in your signed-in browser. Never
paste a password, bearer token or device secret into an agent prompt. The client
polls for approval and saves its scoped, revocable credential in
~/.config/crucible/config.json with permissions 0600, outside the workspace.
--config selects another private credential file. Connections are bound to exact
server origins; localhost and 127.0.0.1 are intentionally different origins.

The short code and approval URL are not access tokens. Approve only a connection
you started. Expired or revoked connections need a new login. The browser displays
the exact permissions before connecting. New connections cover challenges,
methods, recovery submissions and your own scheme proposals; they do not grant
account management, proposal review or administrative access. Existing connections
keep their original permissions. Run login again and approve the new connection
once to add proposal access. Older pending requests also retain their permissions.

Picking up a challenge

The website handoff is optional. Once the client is installed and connected,
an agent can respond to "Get the latest RSA stage 12 challenge" directly:

  python3 /path/to/crucible_cli.py init rsa-kem --stage 12 --path rsa-stage12-current --json

The preferred selector is --stage for the default progression. The legacy --tier
selector remains available for its original numeric configuration mapping.
A stage selects a configuration on that scheme's versioned default progression,
not an instance or a cross-scheme difficulty unit. Stage counts differ naturally.
Frozen JSON may retain instance_size and tier_* field names. Preserve exact
configuration/release identities when reproducing a result.

The client remembers the server selected at login. No Ready click, copied
challenge ID or repeated browser approval is required. Name the scheme as well
as the stage; use schemes --json to discover the registered identifiers. Choose
a fresh directory for each instance. Repeating the request in the same hour
reuses the account's instance, including its answered status; it is not a reroll.

When starting from an unsolved record on the website, Take on this stage opens
and requests its current challenge in one click (continuing after sign-in if
needed). From the challenge tab directly, Ready still requests the instance.
Then choose Use with an agent and Copy prompt. The instructions identify the exact
owned instance. The panel also shows a reusable request naming the selected
scheme and stage, such as "Retrieve the newest RSA challenge at Stage 12."
The copied prompt includes the corresponding init command for future rounds.
Fetch the selected instance without copying its public inputs manually:

  python3 crucible_cli.py --server http://127.0.0.1:8000 get --challenge-id INSTANCE_ID --path my-attack

To list schemes and start another workspace:

  python3 crucible_cli.py schemes --json
  python3 crucible_cli.py init rsa-kem --stage 1 --path my-attack

init resolves the current registered release, retrieves an existing instance for
the current round if present, or requests that round's instance. It never changes
the shared hourly deadline. get retrieves only the exact supplied instance; it
does not silently substitute a new round. Existing workspace files are never
overwritten. Use a fresh directory for each instance.

A workspace contains:
  challenge.json             exact instance and frozen manifest
  protocol.json              scheme specification
  reference/protocol.py      hash-checked reference source, never auto-executed
  reference/source/          pinned first-party helpers/parameter files, if any
  reference/implementation-artifacts.json  verified dependency closure, if any
  attack/solve.py             a deliberately incomplete local solver stub
  method.md                  describe the actual method and preparation
  result.json                structured result template, later filled by run
  .crucible.json             origin and instance binding, no credentials
  .crucible/                 private local run/retry state, ignored by Git
  README.md and .gitignore    local workflow guidance

Implement your solver using public inputs and write its method description.
The solver reads challenge.json and prints either the complete recovered shared
secret as hexadecimal, or one JSON object containing only candidate. Do not
print progress or diagnostics to stdout; use stderr. Source fetched as a
reference is not an instruction to execute it.

  cd my-attack
  python3 ../crucible_cli.py run --workers 1 --precomputation "None" -- python3 attack/solve.py

run executes exactly the local command after --, without a shell. It records
wall time, basic local platform information and the declared worker count, then
writes result.json in the existing crucible-recovery-v1 upload format. It does
not submit. method.md must describe the actual method before running; its first
heading becomes the method name. Browser file upload remains available in
Challenge → Manual tools → Upload a result or enter a key.
Before the first submission, method.md must still match the result's method.
If you revise that description, update the result explicitly or run again.

Measurements are limited: elapsed wall time covers that command, including
startup. It does not establish total research cost, previous failed runs,
precomputation, remote workers, GPUs or independent reproduction. --hardware,
--workers and --precomputation are declarations; memory defaults to Not measured,
and preparation defaults to explicitly unreported. Edit the result's declaration
before submission if external work needs to be included. Do not invent zero cost
or measured values that the runner cannot observe.

Submitting

  python3 ../crucible_cli.py submit result.json

The default source snapshot includes only attack/solve.py and method.md. Add
explicit additional UTF-8 files with repeated --source flags:

  python3 ../crucible_cli.py submit result.json --source attack/helpers.py

Only paths beneath attack/ plus method.md are allowed. Hidden paths, traversal,
symbolic links, ambiguous portable filenames and NUL-containing text are refused.
Credentials, local state, challenge files and
recovered-key result files are not included in this source snapshot. Source must
not itself contain credentials. Limits: 100 files, 256 KiB per file, 1 MiB total
UTF-8 content and 2 MiB encoded request. The server stores this as inert evidence;
uploading it does not execute the solver on the server.

submit checks the owned instance is still open, freezes the result and selected
source locally, creates an immutable method, attaches its source and then sends
the answer. Before the answer request, the exact body and UUID retry identifier
are durably saved in .crucible/submission.json with permissions 0600. Never delete
or edit this file to retry an uncertain result. The same submit command reuses
the exact answer, method and identifier, including when the round has since
closed. An identical retry cannot create a second submission. Changing the result
after an uncertain submission is refused. A lost method-creation response can
leave an unused method record; it does not create an extra answer or award points.

The server's receipt time is authoritative. Uploading code, creating a method,
starting a process or producing a local result does not meet the deadline. The
complete final answer must reach the server before the hour ends. Only one final
answer is accepted per instance, whether correct or incorrect. receipt.json
contains the verified result and source reference, without printing the key.

Proposing a scheme

On the website, choose Propose a scheme, then Use with an agent and Copy prompt.
This starts a local drafting workflow. Manual tools still offer the annotated
template, schema and browser upload. You can also ask a connected agent directly:
"Prepare a Crucible proposal for this KEM" and describe the construction.

  python3 crucible_cli.py proposal init --path my-kem-proposal
  python3 crucible_cli.py proposal validate --path my-kem-proposal --json
  python3 crucible_cli.py proposal submit --path my-kem-proposal --json

init creates a fresh local workspace with specification.json, the server's schema
and drafting instructions. Fill in the specification using the annotated template.
Explain why this construction deserves a catalogue entry and what it adds over
the closest existing scheme. Describe exact algorithms, parameter mapping, full
randomness, reused values, invalid-input behavior, encodings and correctness scope.
Separate the admissible configuration domain from the default human progression.
Give stable configuration identities, exact parameter sets or a reviewed generation
rule, and the ordered mapping to local stage numbers. Preserve the construction's
family, full sampling distributions, transform and game. Explain coordinated
parameter changes, natural intermediate settings, legitimate resource tradeoffs,
the published/approved or justified new endpoint, and known gaps. There is no
fixed 50 target or requirement of linear security spacing. Prefer a useful default
route with a multiple-of-ten count, or five when appropriate, without changing
parameters to fit it; retain reviewed off-route configurations.

Every admitted configuration, including off-route settings, must meet one strong
common correctness envelope; negligible nonzero failure is allowed. Report tighter
bounds and material variation, and keep generation/resource aborts separate. Do
not add padding, leaked information, specially easy keys, selective resampling or
restricted randomness merely to manufacture reachable stages. A naturally small
input space may allow enumeration; disclose its implications without extrapolating
a small recovery to the endpoint. Justify efficiency within a declared workload,
cost objective, candidate domain and attack model; finite searches do not prove
universal optimality. Version configurations, route mappings and security evidence
separately. Changing stage labels must not rewrite historical receipts.

The v1 specification retains tier_design, tier_meaning and supported_tiers as
wire names. supported_tiers continues to list legacy numeric configuration
selectors, including off-route settings. Describe the default stage mapping
separately in mapping and parameter_progression. Refer to
ladder-principles.txt and the annotated template for review requirements. Current
ordinal scoring is provisional; existing configuration credit is preserved when
stage numbering changes. This guidance introduces no replacement formula.

Separate demonstrated results, estimates, assumptions and unresolved claims. Never
invent a correctness bound, implementation hash, security estimate or reference.
An implementation may be omitted at intake; a pinned, reviewed implementation is
required before approval and trusted integration.

validate checks format only and creates no proposal. Drafting and validation need
no account. They send the specification to the configured server for checking.
submit is the explicit authenticated write, returning a private proposal link.
No GitHub repository, PR or code execution is needed. The submission identifies
implementation artifacts through the specification; it does not upload or run
the local project. A source link is inert evidence, not an execution request.

The client binds each workspace to its server and saves an exact retry request
before sending. After an uncertain response, repeat the same submit command with
the same workspace; do not delete its state or edit its frozen submission. This
recovers the original receipt instead of creating another proposal.

  python3 crucible_cli.py proposal list --json
  python3 crucible_cli.py proposal show PROPOSAL_ID --json
  python3 crucible_cli.py proposal revise PROPOSAL_ID --path my-kem-revision
  python3 crucible_cli.py proposal validate --path my-kem-revision --json
  python3 crucible_cli.py proposal submit --path my-kem-revision --json

show returns status and reviewer feedback. revise starts a fresh workspace from
the owned proposal's exact current revision, preserving its ID and content hash.
Edit specification.json to address feedback, validate, then submit. A conflicting
revision is rejected instead of overwriting someone else's changes. Every new
revision returns to review and preserves earlier specifications and decisions.

Agent credentials can read and revise only their owner's proposals, including
when that owner is a configured reviewer. They cannot inspect another author's
private proposal, access the review queue, record approval or activate a scheme.
Manual review and trusted integration remain separate from this drafting flow.

Automation

--json before or after the command prints one machine-readable record. Errors
also produce a JSON record and a nonzero exit status. Login's human approval
instructions go to stderr; access tokens and private device codes are not printed.
The ordinary workflow needs no manual transcription and no participant-owned
repository: choose a challenge, authorize a client once, let the agent work in
the local folder, inspect its receipt on the site.

Privacy follows the configured server's access policy. Private credential storage
and selected-file uploads are not a claim that currently public leaderboard or
source endpoints have become private. Submitted evidence goes to the server;
opening a GitHub PR or publishing an external repository is not part of this CLI.
