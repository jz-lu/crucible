Next audit: separate three questions

Stage construction: does each configuration authentically instantiate the
declared family? Is the correctness envelope acceptable without making later
stages unreliable? Are there avoidable inefficient parameter choices? What
supports the progression order and endpoint? More stages and smoother curves
are not scientific improvements by themselves.

Measurement: trace each plotted value to the exact configuration, implementation,
workload, instrument and raw evidence. Check encoded lengths, operation boundaries,
warm/cold calls, RNG/allocation/setup treatment, sampling, unsuccessful attempts,
machine/compiler identities and stale evidence. Investigate irregularities without
smoothing them away. Distinguish mathematical cost from a particular implementation's
runtime. Review the currently active reports, not only dated benchmark summaries.

Presentation: distinguish costs to honest users, modeled attacker work, and actual
recorded recoveries. Do not imply that an attack-work estimate is a proved security
lower bound, that stage numbers are comparable across schemes, or that the highest
recovery proves every smaller setting was recovered. Explain unknowns through the
scheme's supporting notes, with detailed evidence available on demand.

Current notes checkpoint

Sections use deterministic note-and-heading references. In note 56, the second
section is 56.2; its first subsection is 56.2.1. The short resolver includes the
saved revision: GET /api/notebook/locs/56.2@3. Reads/copies do not allocate a
counter or mark a section as cited. Human labels omit the revision (Assumption
56.2, Lemma 56.3, or Section 56.4); the kind follows an explicit author designation,
never an inferred mathematical assessment. A heading margin shows [2] only when
an accessible saved citation or argument uses it. Private incoming uses are not
revealed to other readers.

Saved note reads include section_refs_by_revision, mapping exact passage,
statement or companion-section anchors to these labels and locs. The human
Markdown editor accepts [Assumption 56.2](loc:56.2@3), then resolves and saves a
portable guarded URL with note ID, revision, content hash and exact anchor.
Agents should GET the loc, verify the source and qualifications, and save the
returned URL/reference rather than bare installation-local shorthand. Scientific
dependencies still use the returned exact passage or statement pin, never the
human label alone. Copying a bare number to another installation is not portable.

A section includes its subsections until the next same-or-higher heading. Later
edits may change section ordinals; the @revision pin preserves the old source.
Existing P.N aliases and the legacy allocation endpoint remain compatible, but
new UI references never allocate them. Access is checked on every resolution;
numbers do not grant access. CLI: notes resolve 56.2@3; historical P.33 also works.
