CRUCIBLE: NOTES LIST AND READER CANDIDATE
25 November 2026. Local implementation; not deployed.

Purpose
-------
Researchers should be able to scan a stable list, open an argument, and act on
it without first learning the notebook's internal schema. A note has one
reading destination. The list is for discovery; the reader is for understanding,
precise references and continued work. Structured statements remain optional.

Implemented presentation
------------------------
The outside Notes layout is accepted as of 26 November: left upvote gutter,
quiet title and three primary labels, owner publication controls, and a fixed
researcher/date column at the right edge. Editing belongs inside the reader.
Private + Publish, In review + Retract, and published + Retract are the ordinary
owner states. Published notes need no Published label. Numbers are absent from
the list and retained inside the reader for exact citations. Tags are display
labels; searching still covers titles, summaries, tags and note numbers.

The inside is a local candidate with one header and a continuous article.
Its typography and primary label styling reuse the list's visual vocabulary.
Author/date, publication state and owner actions stay separate from subject
labels. The main labels are Proposal (from an actual request), authorship
(Human-written, Human–AI hybrid or AI-written, explicitly self-reported), and
Literature. Other keywords are quiet and neutral.
Routine success messages are screen-reader announcements, not layout-shifting
banners. Failures remain visible. Publication history is absent from normal
reading except actionable feedback. Reviewer audit views retain their detail.

An ordinary human author needs Title and Note. Summary and Conditions remain
optional API metadata, preserved on edits but absent from the ordinary editor
and reader. They are empty when omitted, never filled with invented assumptions.
Authors explain meaningful caveats in the article, close to the relevant claim.
Formal statement/dependency records and scheme specification/admission checks
remain independently validated. Optional prose fields are not substitutes for
those records. A blank conditions field does not establish unconditionality.
The canonical API still carries claim/conditions strings (empty is allowed),
so the change does not invent a second note format or rewrite saved records.

Free-form body content is the default readable note. Sections, statements and
argument structures remain optional. With existing readable sections, Human Explanation
shows their authored prose; Research details shows the original technical body
as plain source. Nothing is generated, abbreviated or rewritten to fit the UI.
No empty alternate mode is shown for a note without a companion explanation.

Articles with at least two linkable headings have a conventional Contents list:
a quiet right column on desktop and above the article on mobile. It follows
ordinary Markdown headings (including subsections), not a scientific inventory.
There is no mixed statement/argument inventory at the top. Short notes without multiple headings remain direct articles. Exact references target their authored headings.

Judgments to revisit after use
------------------------------
The two reading views keep complete technical records available without making
readers process machine scope fields before the article. Long single-body notes now also use the heading Contents list. Ordinary editing uses the prose fields and preserves exact-reference
metadata. Dedicated statement/argument controls belong to review/developer
tooling and the API; they are no longer part of the normal writing interface.

Preserved contracts
-------------------
Note numbers are display references. Exact links still pin note ID, revision,
content hash and, where applicable, section/statement/argument ID. Reading an
exact older revision never silently substitutes a newer one. Links grant no
access. Cached content and actions retain current authorization checks.
Reading-view state is scoped to account/session and the exact note identity;
departure clears it. A precise prose or statement link selects its relevant
view. Editor dismissal, retries, permission checks and scientific review decisions
are preserved. Author visibility now has the separate lifecycle described in
docs/note-publication-visibility.txt. Review-workspace rows and readers keep their previous presentation.

The title's pointer/focus intent uses the existing bounded body preparation
path. Rendering a list does not fetch every note body. Summary search, filters
and pagination retain the existing bounded cache/invalidation design.

Human and agent interfaces
--------------------------
A capability earns a human control through a concrete researcher task, not just
because an API exists. Reading, navigation, editing, publication, contribution
and review are human activities. Structured exports, API guidance and machine
record formats primarily belong in the agent interface. A human-to-agent
handoff belongs where someone is likely to delegate a task, not on every page.
Technical content is not automatically agent-only: formal statements, explicit
conditions and exact citations remain useful to researchers. Prefer a quiet,
contextual affordance over a standing panel when the task is occasional.

Local iteration, 26 November 2026
Human editors start with Note, using the canonical body directly when
there is no separate explanation. New human notes have no separate companion editor. Existing dual-view notes
and their exact content remain intact; Research details is shown as plain
source with stable line references. Selecting Scheme
proposal no longer inserts the guidelines link; specification checks still apply.
My activity note rows open the exact-revision reader directly without expansion.

The arrow toggles one account upvote immediately, without a dialog. Its count
is the number of supporting accounts. A fresh exact-pin read provides the
concurrency version before writing; ambiguous writes retry the same payload.
Browser writes require membership and CSRF. Self-votes, unpublished revisions
and unscoped agent access remain forbidden. Account-scoped vote markers are
batched into list reads. Legacy double ratings count once under support v2.

Notes do not carry bounty contribution labels or backlinks. Ordinary bounty
readers show the task and its sources, with a separate solution-submission
action. Only the review workspace displays the submissions list. Task posters
may submit solutions; approval still requires a reviewer distinct from both
poster and solver. Existing partial records are preserved, but the human form
offers solutions only.

The ignored preview helper supplies Preview Researcher as display attribution
for imported catalogue rows at the user's request. This does not assign account
ownership, change research content, or alter permission checks.

Independent review, 26 November

were addressed before accepting this local reader: ordinary-body Markdown used
an older rendering path; body statements could not be placed by ordinary authors;

argument links lost navigation far down a long mobile page.

The body now uses the existing bounded Markdown renderer and shared statement
placement grammar. Source-line callbacks retain exact passage coordinates even
when prose lines become a single paragraph; no content or hash changes. The
canonical placement validator is shared in intent across Python and JavaScript,

Independent list entry clears scheme-origin navigation. Exact destinations have
a compact context strip with the appropriate return and Note overview; a premise
followed from an argument also offers its exact argument return. This avoids a
persistent toolbar on every short note. It is presentation context, never part
of a scientific citation or permission grant.

Human and scoped-agent publication actions share the same retraction/restore
contract and durable retries. Agent guidance now describes the actual v12
frontier awards and single-account note upvotes rather than the historical rules.
The agent/CLI/pipeline/statement backend run passed 116 checks; migration,
visibility, moderation and screening checks were run separately. This evidence
is local and does not establish production rollout compatibility.

Deliberate remaining boundary: statements have ordinary fields and body insertion;
complex arguments and pinned definition references remain an optional advanced
structured editor. An agent can prepare these records. This is not yet a polished
form for a researcher authoring a large dependency graph entirely by hand. The
reader preserves arbitrary valid records rather than restricting the schema to
what a future human form can express. A small dedicated argument-authoring pass
should be designed against real researcher examples, not improvised here.

The reviewer also caught a dangling-marker trap on statement removal. Removing
a statement now removes only its actual standalone placement from the current
readable body/sections, preserving code/math examples and surrounding prose.
Removal is blocked with local feedback while an argument still depends on that
statement, so the editor does not silently damage the argument's structure.

Historical passage-loc candidate — superseded 27 November
-----------------------------------------------
A loc is now an actual immutable reference such as P.33, not a heading ordinal.
P means passage. A neutral prefix avoids attaching a mathematical classification
or implied approval to the identity. The author's heading still says Assumption,
Lemma, or whatever the article needs. This is the chosen default for review.

An unreferenced Markdown heading has a quiet citation icon. Explicitly opening
that control reserves a loc; a cited heading displays [P.N] instead. The loc
resolves to one exact note ID, revision, source hash and bounded heading range.
Anyone permitted to read the source can cite it, with appropriate agent write
scope; the author need not register statements or change the note. Ordinary
reading, rendering and navigating never allocate locs. Concurrent/retried
allocations converge on the same source reservation. Reservations survive
deletion without retaining authored text and are never reassigned.

The reader accepts the copied loc URL and selects the pinned passage, never the
latest revision. A restrained highlight shows what was cited, including child
headings and excluding the next same-or-higher heading. Navigation sits outside
the excerpt. The normal article has no statement inventory or duplicated prose.
The source's access rules are checked each time; knowing or guessing a loc is
not authorization. Anonymous, private, retracted and deleted sources do not
become readable through a citation. Historical sources keep historical pins.

Agents allocate with POST /api/notebook/locs and resolve with GET of P.N. The
response includes the excerpt and a self-describing exact reference for argument
dependencies/conclusions. Normalized pins remain the scientific interchange
format, so exports do not rely on a mutable alias and older records still work.
Loc URLs also form existing note-revision graph edges and can be cited as
implementation evidence, with the same source checks. No scientific approval
or adoption follows from assigning a loc.

The deliberate tradeoff: a loc belongs to one saved revision, not a living
section across revisions. An edited note receives new locs when cited; old ones
remain exact. This is less magical and protects research reproducibility. The
installation owns its namespace: importing another site's P.N must resolve its
original source, never assume a local number is equivalent. An exact_source URL
is available alongside the guarded loc URL. UI loc metadata stays outside authored
content and hashes. Existing explicit statement IDs remain supported.

Schema migration 0036 follows the local 0035 chain. It adds only notebook_locs;
no old notes are rewritten or backfilled into arbitrary locs. Apply the normal
migration process before a hosted application requires the table. This pass is
local only and does not claim rolling-upgrade compatibility or change the host.

Portability check: two installations can both have P.1. Copied browser and agent
resolver links therefore carry the exact source identity as well as the loc.
The graph, passage context, implementation evidence and reader check that pair.
A mismatched import cannot silently retarget the other installation's P.1. Bare
loc lookup remains an explicit API/CLI operation on the configured server, not
an accepted portable citation. An isolated two-installation export/import test
covers this failure mode without rewriting historical authored content.

Loc metadata adds one indexed read per selected note source, cached within the
request. Note list payloads do not carry it; curated sources use one bounded
metadata query. No model calls or new service are involved.

27 November — current derived section reference design

Sections use deterministic note-and-heading references. In note 56, the second
section is 56.2; its first subsection is 56.2.1. The short resolver includes the
saved revision: GET /api/notebook/locs/56.2@3. Reads/copies do not allocate a
counter or mark a section as cited. Human labels omit the revision (Assumption
56.2, Lemma 56.3, or Section 56.4); the kind follows an explicit author designation,
never an inferred mathematical assessment. A heading margin shows [2] only when
an accessible saved citation or argument uses it. Private incoming uses are not
revealed to other readers.

Saved note reads include section_refs_by_revision, mapping exact passage,
statement or companion-section anchors to these labels and locs. The human
Markdown editor accepts [Assumption 56.2](loc:56.2@3), then resolves and saves a
portable guarded URL with note ID, revision, content hash and exact anchor.
Agents should GET the loc, verify the source and qualifications, and save the
returned URL/reference rather than bare installation-local shorthand. Scientific
dependencies still use the returned exact passage or statement pin, never the
human label alone. Copying a bare number to another installation is not portable.

A section includes its subsections until the next same-or-higher heading. Later
edits may change section ordinals; the @revision pin preserves the old source.
Existing P.N aliases and the legacy allocation endpoint remain compatible, but
new UI references never allocate them. Access is checked on every resolution;
numbers do not grant access. CLI: notes resolve 56.2@3; historical P.33 also works.
