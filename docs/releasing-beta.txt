Releasing the private beta
==========================

Normal development uses a branch and pull request. The stable branch-protection
check is "CI passed" in the CI workflow. A repository administrator must require
it and protect main; write access alone cannot establish that rule. This check
means portable Python tests, migrations, the explicit critical research/account
workflow gate, frontend regressions, disposable Chromium
browser checks, actual SQLite/PostgreSQL 17 metadata-query parity, and the reviewed
runtime source contract passed. The exact portable workflow selection lives in
tests/run_critical_workflows.py and fails on skipped checks. See
docs/browser-checks.txt for the browser fixture and its scope. It does not mean native workers were rebuilt or
every backend/platform test ran. Optional PostgreSQL fixtures are explicitly
skipped without their dedicated synthetic database configuration.

Release beta is a separate manual GitHub Actions workflow. Choose main, then Run
workflow. Publish and Promote both default to enabled: it builds, verifies and
publishes one app image, then promotes that exact immutable image to the stable
beta tag. Enable Publish and disable Promote to retain a tested immutable image
without updating beta. With Publish disabled it performs the same native checks
without publishing or promotion, regardless of the Promote input.
For a reviewed candidate or schema-bridge branch, select that branch and disable
Promote. Such runs may verify and publish immutable images, but cannot update beta.
Non-main runs with Promote enabled, and all tag-ref runs, are blocked. Source CI
and exact native image checks still run before any candidate publication. Only
main can promote; no app/database credentials or provider-update permissions are
added for candidate builds.
Pushes and merges never trigger this workflow. Moving beta can trigger an existing
App Platform Autodeploy subscription; the workflow itself never edits an app,
its environment or its database.

One-time setup
--------------
Add the repository secret DIGITALOCEAN_REGISTRY_TOKEN. It must have Registry Read and Update permission for
the existing private registry crucible-beta. It needs no app/database permissions.
Each run exchanges this API token for fresh Docker credentials expiring in one
hour, using the fixed DigitalOcean registry endpoint. Credentials live only in
an ephemeral runner's mode-0700 directory/mode-0600 file and are removed in an
always cleanup step. They are never Docker build arguments or release artifacts.
The API token's own expiry remains separate: choose an appropriate expiration,
record/rotate it, and replace the GitHub secret when it expires. A one-hour Docker
configuration is not a durable GitHub secret. No secret values belong in Git.
A repository administrator can add a protected GitHub environment later; this
initial workflow does not depend on environment features or their plan availability.

The workflow uses native Linux AMD64 GitHub runners and the exact reviewed app
base recorded in deploy/release-runtime.json. The private base must be retained
in the registry: do not delete it during image cleanup. Nothing is compiled or
installed into the crypto runtime on an ordinary release. Python 3.13.17, native
workers, their notices and the reviewed dependency closure come from that image.
No self-hosted permanent build server is required by this workflow.

What is checked
---------------
deploy/release.py prepares only a clean, exact Git commit. Its context contains
explicit source directories and three root configuration files. It never copies
.git, .local, a virtual environment, environment files, credentials or databases.
Complete source directories replace the base copies, so deleting a UI file does
not silently leave the old file in the image. Image files are root-owned and
readable but not writable by runtime UID10001. Build/test networking is disabled.

The source contract freezes scheme implementations and supporting data/scripts,
dependencies, migrations, the central database module, generation policy and runtime budget
configuration. A small explicit list of application modules plus web/docs can
change on the ordinary path. Some application modules also define database models;
the separate fresh-migration/alembic-check gate detects model/schema disagreement.
Schema changes require explicit migration review rather than relying on this path
allowlist alone. New executable modules require deliberate review of
that list. Some documentation is also bound into scheme provenance; the native
manifest check catches such changes even if the source path is ordinarily allowed.
This contract is a guard against accidental drift, not a substitute for reviewing
application changes or a security boundary against someone authorized to rewrite
the workflow and its contract.

The resulting image must validate the whole registry and match the exact raw
manifest hashes for all 32 releases and 1,466 profiles, including archived ones.
It runs the named access/UI, catalogue, projection, math-asset, milestone, scoring
and generation-concurrency regression
batches from the selected commit. These are bounded tests with synthetic local
state, not a claim of exhaustive cryptographic correctness, production capacity
or a full backend suite. The portable source checks run first. Published images
are the exact tested images, not a second rebuild.

Publishing records the full Git SHA, unique run/attempt tag, immutable registry
digest, config digest and test evidence. A digest-pinned remote manifest must
match the tested build's exact image configuration. The summary and downloadable
release artifact contain no application secrets. A failed upload can have remote
side effects; inspect its logs and registry before retrying. A new run/attempt
uses another tag. The immutable digest and unique tag remain the release identity;
beta is only a movable delivery channel. Neither the old unique tags nor the fixed
reviewed runtime base are deleted by this workflow.

The beta channel
----------------
Successful runs with both Publish and Promote enabled copy the single published
manifest to
registry.digitalocean.com/crucible-beta/app:beta using the already-installed Docker
Buildx imagetools command with --prefer-index=false. There is no rebuild, dependency
installation, annotation or platform transformation. The helper hashes the raw
immutable manifest, checks its config against the tested build, then verifies that
beta resolves to exactly the same raw manifest digest. Buildx preserves raw bytes
with imagetools inspect --raw; see the official command reference:
https://docs.docker.com/reference/cli/docker/buildx/imagetools/create/
https://docs.docker.com/reference/cli/docker/buildx/imagetools/inspect/

The existing workflow-wide concurrency group serializes releases without canceling
an active one. Immediately before promotion, the helper reads main directly from
the fixed GitHub remote and refuses a stale source revision. It checks again after
promotion. GitHub and the registry do not share an atomic transaction: if main
changes during that interval, the receipt records that beta was already written
and the run requires inspection. Avoid concurrent manual writes to beta.

Failed checks, failed publication, stale main, verification-only runs and runs
with Promote disabled cannot reach the promotion write. A promotion timeout or
failed readback is different:
the write may have happened. promotion.json records started/attempted state,
expected and observed digest, verification outcome and possible side effects.
The immutable publication receipt is retained even when promotion fails. Do not
interpret a failed workflow as proof that beta was unchanged or automatically
retry/roll back over a newer release. Inspect the receipt and provider status.

Publish without promotion is useful when a separately reviewed schema migration
must precede deployment. It does not perform or authorize that migration. Retain
the original prepared, verified, published and build-metadata receipts from the
run; a later promotion must use that exact tested source and its original run and
attempt identifiers. The helper still refuses promotion if that source is no
longer current main. Do not fabricate new receipts or remove the current-main
guard to reuse an older image. A reviewed operator may instead select its exact
immutable image explicitly. Schema compatibility and a compatible rollback image
must be assessed separately; an old image is not necessarily safe after migration.

The combined researcher-profile/Notes-number release requires schema 0025 before
the new app is promoted. Follow docs/notebook-number-release.txt for the normal
Alembic migration, exact-head startup check, backup sequence SELECT grant and
restore-state proof. The old 0024 bridge/operator packet is insufficient. Build
with Promote disabled until these prerequisites pass; the release workflow does
not migrate a database automatically or waive any existing image/source gate.

Deploying a verified ordinary release
------------------------------------
For the automatic channel, an operator first selects the existing app repository's
beta tag in the existing App Platform web component and enables Autodeploy there.
That one-time provider action is separate from this workflow. Preserve all existing
environment values, database, domain, instance size, command and allowlist. After
that, each deliberately started run with Publish and Promote enabled can update
the website through beta without another app-update credential or repeated
configuration entry.
The reviewed beta-release catalogue has one explicit configuration transition:
deploy its loader before removing the legacy CRUCIBLE_BETA_RELEASES override.
Then approved additions can follow the packaged policy. See beta-release-policy.txt.
An image-only rollback to a pre-policy release after that removal is insufficient:
restore its saved explicit allowlist too. Original backup image/environment pairs
remain valid; prefer a verified policy-aware image as the subsequent rollback point.
DigitalOcean documents the existing component's Settings → Source → Edit controls
and watched-tag behavior here:
https://docs.digitalocean.com/products/app-platform/how-to/deploy-from-container-images/

If the provider is still watching a unique tag/digest, promoting beta does not
update it. Either keep manual selection of a verified immutable release, or
perform the one-time channel setup deliberately. Registry promotion proves the
image identity, not that the hosted service is healthy or even running that image.
Wait for the provider deployment to complete, then check health, anonymous
private-route denial, sign-in and the changed user flow. Keep the previous working
unique tag/digest. To roll back, select it in the existing web component rather
than rebuilding old code; disable channel Autodeploy until the next intended
release if necessary. Do not replace environment values during an image rollback.

Readiness at /health includes source_revision when the image contains a valid
SOURCE_REVISION marker. Compare it with the released Git SHA to verify backend-only
rollouts whose browser files have not changed. The marker is the fixed metadata
already checked during image verification; it is read once at startup, never
inferred from local Git or environment variables. Local builds without it omit
the field. The database readiness check and /health/live behavior are unchanged.

An ordinary web-only release does not require rebuilding or rebinding the
scheduled backup job. Its declaration continues to identify its own immutable
backup/code release and unchanged runtime configuration. Preserve that image,
declaration, original server key and encrypted recovery evidence. The release
receipt records the retained reviewed backup image as provenance, not as a claim
that this workflow inspected or changed the provider's backup job. A restore may
use the preserved backup/code release or a separately verified compatible newer
app image. Never label an old backup as created by the new website image.

When the ordinary path refuses a change
---------------------------------------
Scheme, Python/dependency, native artifact, schema, runtime configuration, budget
or backup changes need a separate reviewed release. Do not update contract hashes
merely to turn CI green. Build/test the new runtime, compare declarations and
implementation identities, preserve old receipts, and use the existing explicit
implementation-build admission process where needed. Schema/configuration changes
also require a migration and paired backup/recovery plan. CI never migrates a live
database, approves an implementation or invents a correctness/security review.

Maintenance locations
---------------------
.github/workflows/tests.yml          portable checks and stable aggregate
.github/workflows/release-beta.yml   intentional native build/test/publication
deploy/release.py                    source/context/runtime/publication checks
deploy/release-runtime.json          reviewed base, frozen files and manifests
tests/test_release_pipeline.py       offline tests; no credentials or Docker

The initial native runtime was reviewed outside CI and retained by digest. Verify
setup with a successful GitHub release run after the secret and committed main
are available; offline tests alone do not demonstrate an operational workflow.
