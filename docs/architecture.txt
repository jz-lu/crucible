CRUCIBLE ARCHITECTURE / API

Run ./run.sh and open http://127.0.0.1:8000. The same server serves web/ and the API.
A static file URL is not enough for the working application. The source is shared
for collaboration; the hosted service has not been deployed or cleared for public
operation.

Persistence and boundaries

SQLAlchemy tables store accounts, hashed sessions, immutable methods, challenges,
one final submission per challenge, rate buckets, correctness incidents, and
versioned findings. Alembic migrations version the schema. SQLite serializes write
transactions with BEGIN IMMEDIATE; PostgreSQL uses account/challenge row locks.
Database uniqueness backs both. The local concurrency tests exercise SQLite.

The round is derived from UTC epochs; no hourly background job is needed. Unique
instances are generated on demand within the shared hour. A future expensive KEM
adapter may need a worker queue and atomic publication; do not execute arbitrary
proposal code inside this server.

KEM generation returns public inputs, private Encaps target, and private diagnostics
separately. Public serializers explicitly select fields. Only a challenge-bound
HMAC verifier of the target is retained, not the private exponent, encapsulation
randomness, submitted answer, or raw shared key. The app secret is separate and
persistent; protect it and backups. Python cannot guarantee temporary-memory erasure.

The complete bounded request body receives a server timestamp before parsing.
Acceptance requires received_at < ends_at. Malformed bodies do not consume the
attempt. The answer and idempotency commitment are committed atomically. Exact
retries return the same receipt; changed content with the same retry ID is rejected.
No client timestamp is trusted. The server clock must be synchronized in deployment.

Accounts use Argon2id hashes, random opaque cookies, one-way session-token storage,
login rotation and logout invalidation. Cookies are HttpOnly/SameSite=Strict;
production uses Secure and __Host-. Writes require the configured Origin, JSON,
and session-bound X-CSRF-Token. Allowed hosts are explicit. Credentials and answers
never go into browser storage. There is no email verification/reset service yet.

Bodies are capped at 64 KiB with a 10-second receive timeout. Validation errors omit
input values. Database rate buckets guard costly mutations and session issuance.
IP limits use the ASGI peer; do not trust arbitrary forwarded-IP headers. Configure
body, concurrency and proxy limits separately before public deployment.

The browser renders untrusted content as text. External research links require
HTTPS and are not fetched by the server. A restrictive content security policy
blocks inline scripts. Pseudocode and complexity expressions are never evaluated.

Automation

GET /openapi.json describes request schemas. Use a cookie jar; GET /api/session,
then send its csrf_token as X-CSRF-Token and the configured Origin on every POST.
Login/register rotate both session and CSRF token. Keep credentials out of public
logs, source control and shell command-line arguments.

Challenge tier selection

The visible selector is Challenge tier; the compatible API field remains the
integer instance_size, scoped to a scheme and release.
Scheme metadata describes its size_parameter. The registered mapping determines
exact parameters; manifests and public challenge contracts retain instance_size
alongside the full parameter vector, encodings, and release identity.

POST /api/challenges accepts exactly one of these selection forms:
  {"scheme_id":"teaching-dh-kem","instance_size":21}
  {"profile_id":"dh-v5-tier-21"}
Both resolve to the same profile, so switching forms cannot obtain an extra
instance. The current registered release supplies the mapping for new issuance.

DH5 and RSA2 each register tiers 1–50 under the frozen classical-baseline-v1
reference. Tiers 1–25 target 8–32 reference bits, then reach128 at Tier 50. Tier and
actual field/modulus/subgroup sizes are separate. Estimates are limited rho/NFS
references rather than security guarantees or measured costs. Both still output
32-byte shared secrets. New profile IDs and source releases isolate old ladders.
See security-calibration.txt for exact mappings and model limitations. Accept
only registered parameters; never derive an unsupported profile from a tier.

Round access

GET /api/challenges is read-only. Its round_started flag and
round_started_round_id report whether this account has any issued instance for
this exact scheme/release/current UTC hour, using one clock snapshot. A manual
POST starts the round by issuing the selected tier. Subsequent tiers are issued
on demand when opened in Challenge; no bulk generation occurs. The browser does
not issue challenges while viewing Leaderboard or Protocol, or previewing a slider.

Automatic POSTs include active_round_id. Before pinning or generation, the server
requires it to match the current hour and an existing challenge for this account,
scheme, and exact release. Stale or unstarted automatic requests return 409. Manual
requests omit this guard. Successful responses identify their issued round;
repeat requests reuse the same instance. Account, scheme, release, and hour
boundaries require a new explicit start. Generation failures never activate access.

Scheme descriptors expose profile_metrics and profile_metrics_basis separately
from frozen manifests. Public-key/ciphertext lengths count canonical binary bytes;
unknown lengths remain null. Encodings exclude JSON/hex wrappers and registered
shared parameters. The catalogue's selected metric changes display/sort order;
it never changes which actual recovery supplies attribution or its source link.

compute includes hardware, workers (positive integer), wall_seconds, precomputation,
peak_memory, and optional notes. Candidate encodes the complete shared secret as
hexadecimal, with the exact byte length declared by shared_secret_bytes in that
challenge's stored manifest. Teaching DH-KEM uses 32 bytes (64 hex characters);
this is independent of instance size. Generate one UUID idempotency_key per logical
submission and preserve it on retry. Methods are immutable; a change creates a new
method ID.

Research endpoints:
  GET  /api/targets
  GET  /api/contributions?target_id=...&limit=20&before=...
  POST /api/contributions
  GET  /api/contributions/{id}?limit=20&before_revision=...
  POST /api/contributions/{id}/revisions   author only; expected_revision required

Findings identify target/version, profiles, title, claim, conditions, body,
computational model and evidence kind. Optional fields hold an HTTPS artifact,
time/memory/success expressions, related record and supporting recovery. Append-only
revisions preserve the original. A supporting recovery is server-checked; review
of the finding is a separate fact. Numerical answers do not automatically create
research findings. An unanswered challenge is not a documented investigation.
History defaults to 20 revisions (maximum 50), with next_before_revision for older
pages. The latest field always identifies the current revision, even on older pages.
Source fingerprints are pinned per scheme version. When upgrading older databases,
the first pin must agree with existing challenge manifests; changed or missing
provenance stops issuance until the release is reviewed and versioned correctly.

Release compatibility

Teaching adapter release 2 registers every integer instance size from 20 through
36; n maps to a subgroup order with n bits. Its original five profiles and KDF
domain are unchanged. Release
1 is archived byte for byte rather than reconstructed from the newer adapter.
The example solver supports both releases. Existing challenges and answer receipts
continue to use their recorded release, manifest, and target verifier.

The leaderboard defaults to the current release. Set scheme_version=1 to inspect
historical records for a release-1 profile; records from different releases are not
silently combined. GET /api/protocol/source?version=1 returns the archived source.
Research history retains the exact target release, and findings about registered
older releases remain revisable. Historical source files must not be edited when
updating the current adapter.

Candidate admission

No public admission/upload endpoint exists. A future candidate needs a pinned
specification and adapter, encodings and exact profiles, correctness argument with
scope/assumptions, independent review, conformance vectors and a failure policy.
The current route admits only the explicit teaching lane. Nonzero honest failure
distributions need their own reviewed policy; never silently condition sampling
on agreement or generalize the toy adapter's fault rule to arbitrary KEMs.

Before public release: test PostgreSQL/migrations/concurrency and profile-wide
holds; configure proxy/body/concurrency limits; decide account recovery, identity,
moderation and abuse controls; test backup/restore and secret custody; provide
monitoring and incident resolution; archive each version's exact implementation;
conduct independent application and cryptographic admission review.

Calibrated generation and graph evidence

DH5 public groups and exact primality certificates are embedded in its pinned
source; no live prime search. RSA2 creates fresh balanced certified-prime factors
with candidate, pair, and five-second monotonic generation limits. Exhaustion
returns no instance and is retryable; arithmetic agreement failures still pause
the profile. Expensive generation runs outside database transactions. Before
persisting, a short final transaction rechecks session/account, hour, source,
registered manifest, active-round permission, duplicate issuance and holds.
Overview graphs plot exact profile values and the frozen initial estimate.
A thin red line marks the largest recorded recovery for that release; faint
left shading is a progress cue, not evidence of individual smaller recoveries.
