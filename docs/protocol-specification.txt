CRUCIBLE KEM SPECIFICATION, VERSION 1

Purpose and limits

The JSON format identifier is "crucible-kem-spec-v1". This is a common,
human-readable description of a proposed KEM. It is not executable code, a
machine-checked cryptographic proof, or an automatically admitted challenge
adapter. Validation checks types, required sections, internal labels, document
size and link syntax. It cannot establish that the algorithms implement the
description or that an author's correctness/security claim is true.

An implementation is optional for initial submission. Activation requires a
reviewed reference artifact with an exact SHA-256 fingerprint, explicit human
review, and a separately admitted adapter. An author's name/version or URL
never gives authority to replace a registered scheme or bind to its identity.
The reviewer-controlled decision and adapter binding belong outside this JSON.
Passing JSON validation, entering review, and activation are distinct events.

Files are UTF-8 JSON and must fit 48 KiB (49152 bytes). The compact input and
normalized document also have a 48 KiB ceiling. The existing API request limit
is 64 KiB for the complete wrapper; a caller must fit both limits. No NaN,
infinity or unpaired Unicode surrogates are accepted. No extra properties or
type coercions are accepted. Integers cannot be booleans or quoted numbers.
Required prose is trimmed and must remain nonblank. All counts below are
character limits unless explicitly measured in bytes.

Common structure

Required top-level fields:

  format: exactly "crucible-kem-spec-v1"
  name: nonblank string, at most 100 characters
  version: nonblank string, at most 32 characters
  summary: nonblank string, at most 1000 characters
  algorithms: object described below
  parameters: object described below
  encoding: object described below
  correctness: object described below
  security: object described below
  references: array described below (may be empty)

Optional top-level fields:

  implementation: artifact object described below, or null; defaults to null
  tier_design: stage-progression and parameter-selection plan below, or null;
               optional at intake, required for new approval/admission
  _instructions: object of nonblank string keys and values, at most 32 entries;
                 keys at most 100 characters, values at most 4000 characters

If _instructions is supplied it must be an object, not null. This is template
guidance only. It is validated and then removed from the stored normalized
document and content hash. Absent/null tier_design, its parameter_selection,
implementation.artifact_sha256, encoding.private_key and correctness.justification
remain omitted to preserve older canonical content. Other optional/default null
fields are retained. Existing documents without the new review fields are still
valid drafts and readable historical records; they need a new revision and review
to satisfy current approval/admission requirements. Built-in descriptions do not
automatically acquire a proof or reviewed status.

algorithms

All four fields are required nonblank strings, at most 6000 characters each:

  setup: public setup, parameter validation and setup trust assumptions
  keygen: inputs, outputs, secret/public state, randomness and checks
  encapsulate: inputs, outputs, randomness, public-key checks and derivation
  decapsulate: inputs, outputs, validation and invalid-input behavior

Specify whether invalid public keys/ciphertexts cause explicit rejection,
return a replacement/rejection key, or have some other specified result.
Describe all relevant checks, byte framing and KDF domains. Supply pseudocode
sufficient for independent implementation: exact arithmetic and distributions,
retries/termination, private state and lifetime, and every rejection branch. Define
helpers or cite an exact standard/version/section and its conventions; a bare
instruction such as "decode" is insufficient. A published standard may specify
an unchanged operation, but authors must identify any adaptation and why the cited
operation applies. No programming language or proof assistant is mandated.
The text is never executed. The validator requires nonblank descriptions but
cannot determine completeness or mathematical truth; reviewers assess both.

parameters

All fields are required:

  tier_meaning: string, at most 1000 characters
  supported_tiers: one of the two exact objects below
  mapping: string, at most 6000 characters
  distribution: string, at most 6000 characters
  reuse: string, at most 3000 characters

The two supported_tiers representations are:

  {"kind":"range","min":20,"max":40,"step":1}
  {"kind":"list","values":[20,24,28]}

A range includes both endpoints, has positive step, max >= min, and max lies
on a step from min. A list has 1..1024 unique integers in increasing order.
Every legacy numeric selector and step is a strict integer from 1 through 1000000000. Parsing a
range does not expand it or make the listed stages available as challenges.

These are legacy v1 wire names. supported_tiers retains numeric configuration
selectors, including reviewed off-route settings; tier_meaning explains them.
User-facing terminology is stage. A stage is an ordinal on this scheme's versioned
default progression; a configuration is the stable exact parameter setting or
fully specified reviewed generation rule it selects. A challenge instance is one sampled public key/ciphertext at that setting.
Describe the admissible configuration domain separately from the ordered default
route, using tier_meaning and mapping. Give stable configuration identities and
an explicit mapping. Other reviewed settings can belong to the same scheme.

Default stage ordinals run 1..N and map separately to configuration identities.
Prefer a multiple-of-ten count, or five when appropriate, if natural settings
support a useful route; this is not a scientific requirement. Preserve off-route
configurations. Legacy selector values and historical documents remain valid.
Specify complete distributions, randomness, rejection and conditioning; identify
public, secret and reused values across setup, keys, instances, accounts and
rounds. Equal stage numbers or fractions of a route do not establish equal
security or attack cost. Proposed ranges/generation rules never automatically
issue challenges or authorize unreviewed parameters.


tier_design (legacy name for the stage-progression plan)

Optional for historical documents and intake drafts. New approval/admission
requires all seven fields below and the parameter_selection object, plus explicit
manual stage-design and parameter-selection checks. Each field is a nonblank
string up to 4000 characters, except endpoint_target (2000) and endpoint_status:

  parameter_progression: admissible configurations, the ordered default route,
      natural parameter scaling, preserved family/distributions/transform/game,
      stable identities, and route revision policy. Coordinated changes in more
      than one parameter are permitted with justification.
  cost_tradeoff: communication/computation/memory costs and measured-versus-modeled
      evidence; explain legitimate plateaus and competing objectives.
  fixed_correctness: one strong common correctness envelope covering every admitted
      setting, including off-route settings. Negligible nonzero failure is allowed;
      disclose tighter bounds and material variation. Keep resource aborts separate.
  endpoint_status: supported-estimate, provisional, or unestimated; not certification.
  endpoint_target: the published/approved reference setting where applicable, or
      a justified reference endpoint for a new construction. No standard strength
      follows merely from being the last stage.
  endpoint_evidence: pinned models/sources, their domain and limitations, native
      input-space limits, uncertainty, and missing evidence.
  intermediate_steps: useful natural settings and any omissions or coarse gaps;
      a round-count default is a presentation preference only. Preserve useful
      off-route configurations; linear security spacing is not required.

parameter_selection contains six nonblank text fields:

  objective: cost objectives, units and workload, or Pareto tradeoffs (3000 chars)
  constraints: family, game, common correctness and implementation constraints (3000)
  security_model: pinned attacks, estimator versions, units and assumptions (4000)
  search_domain: candidate domain, coverage, excluded choices and filters (4000)
  comparison_evidence: reproducible comparisons and scoped selection argument (4000)
  tradeoffs_and_uncertainty: alternative objectives, model gaps and exceptions (4000)

Reject artificial padding, leaked bits, specially easy keys, selective resampling
or restricted entropy used solely to manufacture easy stages. Naturally small
input spaces may permit enumeration; disclose it without extrapolating recovery
to larger settings. Finite candidate comparisons do not establish global
optimality. Fidelity takes priority over improving an estimator's output.

Version exact configuration identity, the progression mapping and security evidence
separately in the prose and integration record. Adding/reordering a stage must not
redefine prior configuration IDs or recovery receipts. The current v1 service
binds registered releases/profiles; it does not offer an arbitrary configuration
explorer or independent progression-edit API. These fields describe reviewable
contracts, not executable machinery. Frozen specifications remain unchanged.

Scoring is a separate provisional policy. This format does not award points or
make ordinal distance a scientific measure. Existing configuration credit stays
fixed when a route is curated or renumbered. A denser default route must not imply
a more valuable identical recovery; no new score formula is adopted.

encoding

Required fields:

  public_key: string, at most 3000 characters
  ciphertext: string, at most 3000 characters
  shared_secret: string, at most 3000 characters
  shared_secret_bytes: strict integer 1..4096, or null

Optional at intake and required for new approval/admission:

  private_key: nonblank string of at most 3000 characters, or null

Describe private components and their canonical encoding, or an exact internal
representation when serialization is not defined. Include state lifetime and
secrets used for implicit rejection. This is a format description; never upload
actual private-key material as part of a proposal.

Describe canonical binary encodings, field widths, endianness, padding, framing
and JSON/hex transport separately. shared_secret describes the derivation/KDF,
domain separation and exact output encoding. shared_secret_bytes states a
fixed byte length; use null when it depends on the configuration,
and specify the length mapping in shared_secret. Null never means 32 bytes.
No length expression is evaluated by intake. An executable adapter must later
provide exact, machine-usable limits for every admitted parameter profile.

correctness

Required fields:

  kind: "perfect", "statistical", or "unknown"
  failure_bound: nonblank string of at most 1000 characters, or null
  argument: nonblank string, at most 6000 characters
  scope: nonblank string, at most 3000 characters

Optional fields:

  evidence: nonblank string of at most 3000 characters, or null; defaults null
  justification: claim, assumptions and supporting reasoning below, or null; defaults null;
                 required for new approval/admission
  policy_id: "crucible-honest-agreement-128-v1", or null; optional
  failure_bound_exponent: strict integer 0..1000000, or null; optional at intake,
                          required >=128 for new statistical approval/admission

Perfect requires the literal bound "0". Statistical requires a stated bound
string. Unknown requires null. These label-consistency checks do not verify the
bound. State what is unknown rather than supplying a fabricated argument.

The scope must identify admitted parameters, honest keys/ciphertexts, the
probability space and any conditioning, and mathematical/implementation
assumptions. Honest encapsulation/decapsulation agreement is distinct from
security against an adversary. argument remains the explanatory summary; evidence
holds supplemental empirical results/reproduction references. Historical evidence
text is preserved. Tests alone cannot establish an extremely small failure rate.
A new approval requires a claimed bound at most 2^-128 (or perfect agreement)
and reasoning with its explicit premises; those premises may remain conjectural.
A weaker or unknown correctness claim is accepted only as a draft.

correctness.justification, when supplied, has exactly these required fields:

  kind: "mathematical-proof", "analytical-bound", "model-based-analysis"
        or "conjectural-claim"
  statement: exact agreement theorem/failure bound (up to 3000 characters)
  conditions: explicit hypotheses and probability model (up to 4000)
  configuration_coverage: entire admitted domain and case coverage (up to 4000)
  derivation: proof/bound, cited theorem, or rationale identifying unproved steps
              for a conjectural guarantee (up to 6000)

The statement must agree with kind/failure_bound in correctness. Conditions must
identify fixed parameters, public setup, honest inputs, all randomness and
conditioning, RNG/hash idealizations and implementation/mathematical hypotheses.
Conditional guarantees are allowed when their conditions are explicit. Explain
why the result covers every supported configuration, including off-route settings
and the entire domain of any generation rule. Account for all relevant rounding,
decoding and rejection events and parameter-dependent inequalities.

A concise derivation can cite a pinned paper/standard version and exact theorem
or section, with references and an explanation of its applicability to the
submitted construction. Formal machine checking is optional. Empirical success,
a theorem title alone or an unsupported "negligible" claim is insufficient.
The kind label is an author assertion, not proof status. Intake checks shape;
manual review assesses the claim, reasoning and dependencies. Identified unproved
steps can remain conjectural; unclear or misrepresented claims need revision.

Model-based analyses are eligible for manual review. Define the modeled experiment,
derive its bound, identify each unproved bridge to the concrete algorithm and
justify applicability to every admitted configuration. Keep that evidence class
and its assumptions visible; exact calculation within a model is not proof of
the concrete algorithm. Published analysis does not automatically cover reduced
or otherwise changed configurations.

Conjectural claims may be approved for research when they state the required
correctness goal, independently motivated assumptions and the reasoning connecting
them. Tautologically assuming that the target already holds is not a meaningful
justification; identify independently assessable mathematical/algorithmic premises.
Distinguish proved, modeled and conjectural steps; approval does not prove the premises.
Unknown correctness remains draft-only. Both a correctness guarantee and a scoped
security claim are required for manual approval; neither must prove all premises.

correctness.policy_id remains optional; its recognized value identifies the
required claimed 2^-128 correctness goal. For new statistical approval/admission,
failure_bound_exponent must be a conservative integer b>=128 declaring delta<=2^-b
under the stated premises. Round fractional exponents down and review consistency
with the bound text, reasoning and parameter coverage. The server checks the
declaration, not its mathematical truth. Weaker exponents or omitted declarations
are valid drafts, not approvable claims. Perfect/unknown claims omit the exponent;
unknown correctness stays draft-only. Historical omitted fields preserve canonical
hashes. See correctness-policy-v1.txt for scope, abort treatment and refutation
distinctions. A looser upper bound or a broken assumption is not by itself proof
that actual failure probability exceeds the goal; neither is one failing sample.

Reference implementation conformance and safe execution are separate review
obligations. An algebraic proof does not establish that code implements it, and
successful tests do not establish a negligible failure probability. Published
reference timings are separate performance evidence, not correctness evidence.

security

All four fields are required nonblank strings:

  notion: at most 1000 characters
  model: at most 1000 characters
  claim: at most 4000 characters
  assumptions: at most 4000 characters

State the objective/game, adversarial/oracle access, classical or quantum model,
setup/precomputation and cost assumptions, the actual claim and supporting
assumptions. An unfinished draft may identify an absent claim, but new approval
requires an explicit scoped security guarantee. A conditional or conjectural claim
is allowed; state when no reduction is supplied and identify the unproved steps.
Free text is an author's statement, never an executable admission policy or a verified
security category. Recovering a challenge secret is evidence of that recovery;
it is not a lower bound on a scheme's security.

implementation and references

implementation, when non-null, has:

  url: required nonblank URL, at most 2048 characters
  sha256: 64 lowercase hexadecimal characters, or null; defaults null
  artifact_sha256: optional full implementation-closure SHA-256, or null
  runtime: nonblank string up to 1000 characters, or null; defaults null
  entrypoint: nonblank string up to 1000 characters, or null; defaults null

references is an array of at most 16 objects, each with exactly:

  title: nonblank string, at most 200 characters
  url: nonblank URL, at most 2048 characters

URLs must use HTTPS, without credentials, whitespace, control characters or
backslashes, or must exactly match an existing registered source endpoint:

  /api/protocol/source?scheme_id=teaching-dh-kem&version=4

The latter exception identifies a known immutable source artifact; arbitrary
relative URLs, unknown releases, query extras and duplicate parameters are
not accepted. Nothing is fetched, installed, imported or executed during
validation or submission. A linked artifact must later be retrieved and
reviewed through a separate deliberate process. Links do not imply endorsement.

Canonical content and Python entry points

  ProtocolSpec.model_validate(input_document)
  canonical_spec(validated_specification) -> dict
  ProtocolSpec.model_json_schema() -> dict
  template_spec() -> dict
  builtin_spec(scheme_id, version=None) -> dict

The blank template contains required empty placeholders and is intentionally
invalid until completed. Built-in examples are valid documents in this same
format. Their exact version may be specified; omitted version uses the current
registered release. Unknown schemes/releases raise ValueError. No instance or
key is generated to produce an example.

Canonical content is the normalized model dump with defaults/nulls retained,
_instructions omitted, and absent/null tier_design or nested parameter_selection
omitted for historical compatibility. For the stored content hash, serialize that dict
with sorted keys, separators (",", ":"), ensure_ascii=False and allow_nan=False;
encode as UTF-8 and compute SHA-256. This project-specific normalization is
not a claim of RFC 8785 compliance. canonical_spec raises ValueError for a
nonvalidated argument, invalid Unicode or an oversized document; Pydantic
reports model-validation failures as ValidationError.

Historical registered examples

The finite-field Diffie-Hellman examples retain each release's actual ladder:
release 1 has the five tiers 20,24,28,32,36; release 2 has every tier 20..36;
release 3 has every tier 20..128; release 4 has every tier 20..300. The public
safe-prime group is fixed per tier and reused across keys/accounts/rounds;
secret key and encapsulation exponents are independently fresh per new issued
instance. The complete KDF domain, framing and field list come from the exact
release manifest. A public key and ciphertext each encode one group element;
registered p,q,g are separate shared parameters.

The RSA example is release 1 with every tier 20..128. The public exponent is
fixed, while every new issued instance draws new primes and modulus, then a
fresh encapsulated integer. Independently sampled values can coincide. N and
e are each padded to ceil(n/8) bytes in the public key, including the exponent;
the ciphertext is one such integer. This is a custom reference construction
with a transcript-bound KDF, not a standardized RSA-KEM implementation.

Both examples output 32 bytes and preserve the original correctness scope,
argument, implementation evidence caveats, security caveats and exact source
SHA-256. They provide explicit invalid-input rejection behavior. Source hashes
identify the frozen executable release, not certification of its claims.

Admission and the future executable adapter

Intake does not yet encode arbitrary KEMs into runnable challenges. Activation
requires an explicit reviewed bridge from a specification/artifact to a trusted
adapter with stable scheme, release and profile identities. A textual entrypoint
is never dynamically imported. The existing adapter pattern has keygen,
encapsulate, decapsulate, exact manifests and public serialization; a future
general plugin API requires its own deliberate interface and isolation review.

Before activation, the reviewer must assess at least the complete algorithms
and distributions; public/secret/reused state; parameter validity and bounded
generation cost; correctness scope, evidence and known-answer/invalid-input
tests; exact canonical encodings and per-profile output sizes; source/runtime
fingerprints; separation of public challenge data from secret answers; and
version/provenance handling. Admission does not turn a security claim into a
proof. No decision may silently change frozen adapters, relabel prior recovery
receipts, or grant cross-release compatibility without explicit justification.

Current progression guidance

See ladder-principles.txt for the accepted design principles and
stage-progressions.txt for the current per-scheme route audit. Existing built-in
paths are not thereby certified faithful, optimally selected or fully calibrated;
that audit records the outstanding limitations. Schema validation only checks
shape, limits and consistency. Mathematical adequacy remains manual review.
