Linux runtime: isolated build and review
=======================================

Scope
-----
This is a build runbook for a dedicated local Linux VM, not a deployment or an
approval mechanism. Build only a source-only copy of the intended checkpoint.
Do not run these commands in the live Mac checkout or a checkout containing beta
user data. Do not copy .local/, credentials, databases or the Mac .venv into the
VM. A Linux arm64 build is not an x86_64 build: freeze the intended architecture,
exact Python patch version, OS packages and compiler before reviewing outputs.

At this checkpoint registry.py contains 32 registered adapters, including
archived releases. Startup validates all their manifests. The beta allowlist
does not remove the archived build requirements. None of the steps below change
mathematical parameters, profile IDs, scheme versions or source digest checks.
The wrapper deliberately has no 'build everything and activate' operation.

Prerequisites: Ubuntu 24.04 example
---------------------------------
Inside the isolated VM, the operator may install these build prerequisites:

  sudo apt-get update
  sudo apt-get install --no-install-recommends build-essential cmake ninja-build \
    pkg-config libssl-dev python3 python3-venv python3-dev ca-certificates \
    valgrind binutils file

These commands install packages; they are not part of the wrapper. Record exact
package versions and the VM image version before approving a build. Ubuntu's
Python package may receive patch updates: a version pin must use the observed
full patch version, not merely 'Python 3.12'. For a runtime based on another OS or
Python, establish its own equivalent build record. SageMath is not a runtime
dependency; some independent offline certificate/estimator checks require it.
No Sage result is implied by successful compilation here.

For a source-only copy at /opt/crucible-build, as the unprivileged build user:

  cd /opt/crucible-build
  python3 -m venv .venv
  .venv/bin/python -m pip install --only-binary=:all: -r requirements.lock
  .venv/bin/python -m pip install --no-deps -e .
  printf '%s\n' crucible-isolated-linux-build-v1 > .crucible-linux-build-worktree
  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step prerequisites

Use a clean shell without CRUCIBLE_* or database credentials. The marker is an
operator assertion that this is disposable build storage, not proof of that
fact. The wrapper also rejects unexpected .local contents and symlinked output
roots. Its build subprocesses use an empty environment and a separate home under
.linux-build-home. Existing build outputs in this isolated copy may be rebuilt;
some upstream builders replace their own source/output directories. They never
change the application's registry or approve a binary.

Pinned wheels are preferred for the listed Python requirements. If a pinned
wheel is absent for the chosen interpreter/architecture, stop and make an explicit
build decision; do not silently upgrade dependencies or fall back to an
unrecorded Rust/OpenSSL build. Editable installation uses the pyproject build
backend; record the installed build tool versions too. requirements.lock pins
versions, not all downloaded wheel hashes, so retain the exact downloaded wheel
files and checksums for the eventual reviewed release inventory.

Efficient build order
---------------------
Start with two build jobs on a small VM. Increase only after observing memory.
Run each command separately and retain its exit status and stdout/stderr. A
completed step is evidence only for the checks actually run by that builder.

  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step pq --jobs 2 --download
  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step code --jobs 2
  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step hqc-growth --jobs 2
  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step hqc-model --jobs 2
  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step sntrup --jobs 2 --download

Only pq and sntrup accept --download. Their existing builders fetch explicit
upstream source/vector URLs and require the existing SHA-256 values. Omit that
flag when exact source caches have already been supplied. The wrapper performs
no implicit package installation or downloads of its own.

The liboqs base is built once. The code, HQC growth and modeled HQC steps reuse
its verified source tree and static library; none should rebuild that base.
sntrup is independent and can be built in parallel if capacity permits, but do
not run two commands against the same build output root simultaneously.

Known portability boundaries: do not silently patch
---------------------------------------------------
1. NTRU research v2/v3 builders require exact Mac static-library digests for
   librandombytes-kernel.a and libcrypto.a. Both Linux builds will stop at those
   checks. The /usr OpenSSL prefix used for sntrup's -lcrypto reference build is
   insufficient for those scripts' literal prefix/lib/libcrypto.a path on
   multiarch Ubuntu. Inspect the real library path with:

     pkg-config --variable=libdir openssl
     cc -print-multiarch

   A reviewed portability change must select exact Linux dependencies and their
   provenance without discarding the Mac pins. Only after that change is ready
   can build_ntru_tiers.py and build_ntru_frontier.py build these outputs. Do not
   replace the digest constants with whatever was just built. The wrapper does
   not offer these blocked steps or fabricate an approval manifest for them.

2. sntrup.py, ntru_tiers.py, ntru_frontier.py and dhkem_x25519.py contain current
   Mac-specific runtime pins/provenance. New Linux files will not pass them.
   A platform-aware, reviewed implementation-build registration is separate
   work. Preserve historical receipts and existing pins; a new binary does not
   imply a new mathematical scheme or permission to rewrite old evidence.

3. HQC builds use HQC_ARCH_REF, PQCHQC_NAMESPACE_PREFIX and USE_OQS_RANDOMBYTES;
   McEliece uses old_gas_syntax. Those definitions are part of the recorded build
   recipe. Compile unchanged first on the chosen architecture. If GCC reports
   an inline-assembly syntax or unavailable-instruction error, retain the error
   and inspect the exact upstream conditional branch. Do not remove a macro or
   add CPU flags globally merely to make a build green. Any necessary source or
   compiler recipe change must enter the new artifact evidence and tests.

4. liboqs uses a generic target, but NTRU's upstream configure can choose
   CPU-specific implementations. Record host CPU features and compiler choices;
   validate executables on the eventual runtime CPU before distributing them.
   Inspect ELF dependencies with readelf -d; a recorded claim of static crypto
   linkage must agree with the actual NEEDED entries. System libc remains a
   dependency even for the workers with static cryptographic libraries.

5. Pure Python closures can include platform.python_version(). Changing the
   patch version can change their implementation artifact identity. The old
   database accepts one source/artifact pair per scheme version; implementation
   build migration/registration must address this without deleting old pins.

Inventory, review and validation
-------------------------------
After each useful checkpoint, this read-only command reports observed hashes:

  bash deploy/build-linux-runtime.sh --worktree /opt/crucible-build --step inventory

It inventories only explicit native install roots, NTRU worker/manifests and
the installed cryptography primitive files. Missing paths remain explicit.
Its 'approved: false' and 'registry_validated: false' are deliberate: a file
inventory is not proof that those bytes follow from the checked source, nor a
runtime admission. Preserve full builder manifests, sources, logs, licenses,
wheel hashes, toolchain/package inventory and source checkpoint separately.

After the new implementation builds are independently checked and explicitly
registered, run (with an isolated development test data directory):

  .venv/bin/python -B -c 'from crucible.registry import validate_registry; validate_registry()'
  CRUCIBLE_ENV=development CRUCIBLE_DATA_DIR=/tmp/crucible-linux-validation \
    .venv/bin/python -B -m pytest -q -p no:cacheprovider

Use a fresh test directory, never a database copied from production. The full
test suite and registry validation must run on the actual reviewed native
installation, not mocks. Account for skipped Sage/reference-source checks
explicitly. Validate at least the native conformance, NTRU differential/vector,
HQC boundary, McEliece codec and worker integrity/failure tests. A runtime-only
bundle lacks the source/static-library inputs needed by some of these tests;
keep the build tree for validation. See docs/native-setup.txt for test path
overrides. Do not classify a Linux build as ready because source-only CI passed.

New binaries must not inherit Mac performance reports by changing their hashes.
Keep existing reports as historical machine-specific evidence; any Linux timing
report is a separately measured artifact. Finally exercise real PostgreSQL and
concurrent browser/agent flows on the intended server. Neither compilation nor
the preflight command provides those measurements or creates launch approval.

Linux AMD64 preparation, 2026-10-22
---------------------------------
A separate scripts/build_ntru_linux.py preserves the original Mac builders and
source/parameter pins. It accepts explicit verified Linux static dependencies,
records resolved OpenSSL headers and dependency bytes, and emits candidate
workers/manifests in an isolated marked checkout. The actual Debian build needs
libcrypto.a plus explicit ordered libz.a and libzstd.a dependencies. Both research
workers compiled successfully; their ELF NEEDED entries contain only libc.so.6.
This does not yet establish complete conformance or platform admission.

The builder records its compiler driver and selected inputs but is not hermetic: 
not every system header, linker or compiler subprogram is individually pinned.
Retain the recorded build image/package inventory alongside its manifest.
The original Mac build scripts and runtime pins remain untouched.

scripts/build_sntrup.py accepts --build-timeout-seconds (60..3600, default900)
for make-install only. Its configure, worker/reference compilation and upstream
test deadlines stay900s. Timed-out process groups are terminated. The first
AMD64 attempt hit900s under QEMU; retain that failure separately from the retry.
Neither this option nor successful compilation changes server worker limits.

Exact Linux Python3.13.17 wheels are retained and installed offline with --no-deps;
pip check passes after the Linux-conditional greenlet pin. The runtime source
snapshot is explicitly an uncommitted source inventory, not a Git commit.
Four platform-aware runtime adapters and their loader are staged separately.
Before using them, freeze reviewed metadata and source, validate actual manifests,
and record additive implementation reviews anchored to the original Mac release
identities. Never rewrite old receipts or use observed binaries as automatic pins.

All 32 original Mac releases/1466 public profiles were inventoried without opening
a database. This public evidence is retained privately with its exact checksum.
It is not itself approval of a Linux build. Archived releases with no issued
challenges can lack an AdapterVersion row; initialize missing ORIGINAL anchors
only through scripts/beta_release_baselines.py after transfer verification
(see docs/beta-release-baselines.txt),
never by letting an unadmitted Linux runtime choose them on first issuance.

No actual DigitalOcean sandbox, runtime image, cloud database or participant
cutover has been tested. QEMU results must not be presented as native benchmark
measurements or provider capacity. The original ARM64 evidence above remains
separate historical evidence with its exact source/runtime scope.
