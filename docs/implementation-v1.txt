CRUCIBLE — IMPLEMENTATION RECORD, 2026-10-12

This file records the current application, including teaching adapter release 2.
It supersedes the timing and infrastructure proposals in protocol-v0.txt, which
is retained as a historical draft. Source is shared for collaboration; a hosted
service has not been deployed and this is not a production-readiness claim.

Priorities

1. Positive societal value through cumulative, inspectable cryptographic research.
2. Respect attention: clear next actions and progressive detail.
3. Build the attack experience first while preserving a path for proposals.
4. Support automation through structured contracts and APIs.
5. Distinguish verified, reported, mathematically argued, and unreviewed evidence.
6. Do not translate parameter size, key length, or inactivity into security claims.
7. Require correctness evidence for every admitted release and profile.
8. Preserve methods, attribution, revisions, and useful intermediate investigations.
9. Prefer portable interfaces and durable constraints over browser-only state.
10. Make consequential choices explicit and keep unresolved questions visible.

Current behavior

- The numerical objective is recovery of the complete encapsulated shared secret.
  A matching key proves one instance was solved; it is not a full assessment of
  confidentiality, an independently reproduced method, or a verified compute cost.
- Shared UTC rounds open on the hour and close at the next hour. Late arrivals
  receive only the remaining time. Participants compute externally and report
  their pseudocode, hardware, runtime, memory, and reusable precomputation.
- Each account receives an independent instance for each exact profile, release,
  and round. One well-formed final answer is allowed. Identical network retries
  return the original receipt. Multiple accounts remain a target-shopping limit.
- The leaderboard lists the first ten successful accounts per exact profile and
  release by server receipt time. Response elapsed time and reported compute are
  separate quantities. Every submission remains in durable storage.
- Routine numerical runs do not automatically create research findings. A finding
  is an intentional claim, method, partial result, or documented investigation.
  It can cite a verified recovery but remains unreviewed. An unanswered challenge
  is not evidence of an unsuccessful investigation or of security.
- Research targets include schemes and underlying mathematical problems. Findings
  have conditions, evidence, authorship, immutable revisions, and follow-up links.
  There is no universal ranking of theoretical findings or general security score.

Implementation

- FastAPI and plain browser HTML/CSS/JavaScript; SQLAlchemy and Alembic; SQLite for
  local development. PostgreSQL integration and concurrency still need testing.
- Handle/password accounts use Argon2id and server-side sessions. There is no email
  verification, account-recovery service, or moderation system yet.
- DH6 and RSA3 use 50 registered Challenge tiers, numbered1–50. Their frozen
  classical rho/NFS reference targets 8+120(t-1)/49 bits, evenly spaced from
  8 at Tier 1 to 128 at Tier 50. Actual modulus/field/subgroup sizes remain separate.
  Estimates are explicitly limited references, not a security guarantee or
  a one-hour attack-time prediction. See security-calibration.txt.
- Both output 32-byte shared secrets. Tier 50 uses a 3072-bit field/modulus.
  The catalogue shows recovered tier, attribution and participant count; scheme
  overviews show exact size curves, initial reference curves and red recovery
  markers. Timing and quantum-estimate cards remain empty templates.
- Historical automatic-access UI below was superseded on 2026-10-26 by explicit
  requests for each stage; architecture.txt describes the current policy.
- POST /api/challenges accepts either scheme_id plus instance_size or profile_id.
  A first explicit request starts access for this account/scheme/release/hour.
  Later opened Challenge tiers load on demand with an active_round_id guard.
  New hours require a fresh start. GETs and slider previews never issue instances.
- Frozen DH releases 1–5 and RSA 1–2 remain archived with their source fingerprints.
  The calibrated releases have new profile IDs and inherit no old-tier credit.
  The DH example accepts releases 1–6 up to 36 subgroup bits; the RSA example
  accepts releases 1–3 up to 36 modulus bits. These are deliberately bounded
  entry-level public-input solvers.
- Leaderboard and source APIs accept an exact historical version. Newer receipts
  never flow backwards into archived versions. Findings on earlier registered
  releases remain revisable.
- A short algebraic argument establishes perfect correctness of the specified DH
  construction. Executable tests and each instance's round-trip check have a
  separate scope. An implementation fault pauses new issuance for that profile;
  it is never silently retried until a successful instance appears.
- The discrete-log target describes an attack route to the teaching KEM, not an
  automatic equivalence between assumptions or a general security reduction.
- Catalogue entries are curated in code. Uploaded code is never executed, research
  links are not fetched server-side, and complexity expressions are not evaluated.

Decisions to revisit

- First genuine candidate KEM, exact parameters, and independent correctness review;
  admission of schemes with nonzero honest failure probabilities.
- Research admission, moderation, corrections, authorship, identity, and recovery.
- Method families, independent reproduction, and credit for intermediate or
  unsuccessful work that provides useful evidence.
- Narrow theoretical comparisons that justify a table or ranking.
- Outages, data retention, multiple accounts, and public views beyond the first ten.
- A future distinguishing track: security game, statistical qualification, leakage
  controls, and the scope of any resulting claim. It is not the current benchmark.
- PostgreSQL validation, proxy limits, monitoring, backups, incident response,
  independent application review, and public deployment.
