Showcase content and editorial selection
=======================================

Purpose
-------
Introduce a small, legible research pipeline for making and testing cryptography.
The showcase retains beta sign-in and the existing application. Its guides are
working templates, not adopted governance or evidence that a scheme is secure.
The November 2026 presentation uses light mode, without visible RESI branding.

Starting collection
-------------------
Twelve bundled notes remain featured in web/map/notes.json: four guides and
eight scheme dossiers. The guides explain getting started, resource estimation,
posing a new assumption, and how proposals are accepted. Keep their operational
instructions aligned with the implemented pipeline.

Older bundled entries remain archived through extensions.editorial_selection.
The exact revisions of 21 published account notes are excluded from discovery
through web/notebook/editorial-selection.json, following the editorial owner's
selection on 16 November. Three are operational test posts; eighteen are earlier
research notes. This is a release-owned selection policy, not a database mutation.
It takes effect when the application release containing it is deployed.

These choices keep the opening collection small. They do not declare research
false or certify the remaining claims. Existing records, revisions and map
bindings are retained, exact citations continue to resolve, and owners retain
access through My notes. A later published revision needs a fresh editorial
selection; the current exclusion never silently follows changed content.

How to update or restore the collection
--------------------------------------
Bundled content: edit web/map/notes.json. Append a revision for a substantive
content change; never rewrite an existing cited revision. Bundled discovery
choices live outside revisions in extensions.editorial_selection.archived.
Remove an entry there to feature it again, then run python web/map/build.py.
Commit notes.json, catalogue.json when its sources change, and both generated
browser projections together. Do not edit the generated JavaScript directly.

Published account notes: edit web/notebook/editorial-selection.json. Each entry
must name the exact note UUID, revision, SHA-256 and reason observed in the
reader's Record details. Removing an entry restores discovery. A different hash
or a later published revision is not archived by the old decision. Never use
authored note extensions as editorial authority. The bounded policy is separate
from bundled note bodies so damage to that catalogue cannot disable account-only
browsing. There is no new database table or provider-dashboard procedure.

Discovery filters run after choosing the latest readable revision and before
pagination; an old matching revision must not reappear as a fallback. Apply the
same policy to notebook lists, the warm summary index, tags, the timeline and
agent discovery. My notes and authorized exact reads retain access. Archiving
does not grant access, revoke publication, erase history, alter ratings or
certify a claim. Normal moderation and publication permissions still apply.

Bounty briefs
-------------
The board shows actual bounty records. It has no sample/template gallery.
Launch bounties should be ordinary account-authored proposals with precise scope,
reproducible completion criteria and a verification plan. The owner will choose
which briefs to publish and fund from their allowance; no choice, publication or
spending is implied by discussing a candidate. Independent admission and
completion review remain authoritative. Prefer useful work on public crypto
specifications, reproducible comparisons and controlled research fixtures.

Review and release
------------------
Check desktop and phone layouts, direct archived citations, owner access,
latest-revision behavior, pagination and the warm index. Existing regression
suites cover these boundaries. The change uses the ordinary source release path
in docs/releasing-beta.txt; it needs no migration, provider setting or paid
service. Keep docs/operating-budget.txt current when a future feature changes
costs. Automated publication screening and a future scientific review assistant
are different decisions; neither replaces independent scientific review.

An existing generated-evidence freshness issue remains outside this editorial
change: build_display_notes would append revisions to display-evidence-sntrup-3
and proposal-advice. The former changes scientific source/timing evidence. Do
not silently regenerate these while editing presentation; review their pinned
sources and release evidence separately. Both outdated compilations are excluded from the featured collection. Historical
records remain unchanged.

Recovered assumptions design
----------------------------
The November 6 feature/assumptions-note-integration draft at commit 14dd592 adds
exact statement readers, argument views and reviewed roster records. Its local
serve_claims_preview.py is a disposable preview, not a production sign-in bypass.
The statement reader is promising; the opening argument view needs a shorter
explanation before its dense formal details. Carry the current light palette
and simpler branding into any eventual integration.

Do not treat visual polish as backend readiness. Its own review documents still
identify schema/runtime-contract work, PostgreSQL review/withdrawal concurrency
coverage and bounded roster-history reconstruction. Resolve those explicitly
before integrating the full workflow. Keep publication, editorial featuring,
scientific review and scheme activation distinct as this feature develops.
