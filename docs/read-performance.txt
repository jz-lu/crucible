Read-path preparation and metadata SQL

Complete stage recovery summaries
---------------------------------
Catalogue, navigation and progress responses include a release-bound compact
winner summary for every registered stage. Selecting a stage can immediately
show its winner or Unsolved without another leaderboard request. Only the method
name is included; full method/compute evidence still loads when opened.

The summary reuses the existing first-valid-receipt query and retains exact
release compatibility, inherited/exact-profile rules and timestamp/receipt-ID
ties. The catalogue still uses two SELECTs. Frontend validation requires complete
profile coverage and matching release identities; older or malformed responses
fall back to the existing leaderboard endpoint. Explicit Refresh performs a
fresh progress read. Session changes and writes retain cache invalidation.

Local synthetic metadata measurements across 32 releases/1,466 profiles took
5.1 ms for empty summaries and 12.6 ms with a winner per profile. Summary-only gzip
sizes were 5.7 KB and 26.4 KB respectively. These are local preparation measurements,
not a hosted latency or capacity guarantee. Browser checks cover immediate
winner/Unsolved rendering, no redundant per-stage requests, detail-on-demand,
legacy fallback and focus preservation at desktop and mobile widths.

Browser loading and small projections
------------------------------------
The notebook's scheme map renders from its bundled graph without waiting for
the complete profile catalogue or live recovery aggregates. Its action links
use GET /api/schemes?projection=map, a small current-release identity list with
the normal fresh beta admission check. A slow link-index read does not hide the
graph. Opening a scheme can finish/retry that shared read without replacing a
research-note popup or moving focus away from an existing link.

The browser requests summary=true on challenge GET/POST. These responses carry
the same instance identity, deadline, submission status, output length and
download link, without transferring public-key/ciphertext bytes. Default API
responses and exact challenge downloads retain the complete original inputs.
Existing-instance GETs join the submission in the instance query and do not
repeat the already-proven round lookup (three member-read SQL statements,
including both fresh access checks, instead of five).
Summary reads also omit the public-input JSON column from the database query,
including reuse of an already issued instance. Query-scoped raiseload prevents
an accidental property access from silently fetching that large column later.
Output length comes from the instance's stored manifest, which already governs
answer validation. Missing or invalid historical declarations remain readable
with unknown length; full API responses and downloads preserve their inputs.
Generation, ownership, scope, parameter and admission policies are unchanged. Visiting
an exact challenge route starts its read-only status request alongside scheme
descriptions, then consumes that result once. It never speculatively generates.
Previously authorized instance summaries can paint an exact same-round revisit
from bounded session memory while their status revalidates. Instance actions
wait for the fresh read. Rotation, revocation, writes and hour/selection changes
invalidate or separate these views; a failed refresh removes the saved summary.

Database pool checkout exhaustion returns 503 and Retry-After: 2 from both
outer admission and application handlers, with no connection/credential details.
The existing connection cap and checkout timeout remain unchanged. This is a
controlled overload response, not additional capacity or a hosted load-test claim.

tests/test_loading_projections.py covers exact full-download preservation,
small responses, fresh membership, map SQL budget and real pool exhaustion /
recovery. Standalone frontend and Chromium checks hold independent responses
to verify overlap, route/session ownership and an unblocked graph. Timing is
not asserted against a fast local server. Hosted signed-in latency and provider
CPU/database placement still need separate measurement.

Public-site observation, 24 October 2026: three fresh-connection anonymous
/api/session requests took 249–294 ms, while Server-Timing reported 19.85–28.64 ms
inside the application. The no-database /health/live path took 239–347 ms. The
difference includes network/proxy overhead; this is a small developer-machine
sample, not a signed-in challenge or capacity benchmark. Reducing sequential
requests matters even when an individual handler is fast.

Loading presentation
--------------------

Cold catalogue reads reserve the heading and four-column table layout using
neutral placeholders. Heading fonts and spacing match the populated catalogue;
there is no pulsing, stagger or artificial minimum display time. Private scheme
and participant data still wait for fresh session admission. Warm reads retain
the current content when the existing cache policy permits it.

Transient read statuses are visually hidden but remain accessible to assistive
technology. Errors, retry controls, real empty states and submission feedback
stay visible. This is presentation continuity, not a reduction in network time.
Held-response browser checks compare typography and geometry at desktop and
mobile widths; ownership tests cover navigation, access loss and late responses.

Profile previews share the username, back line, statistic cells and folded record
sections with the completed page. Counts remain blank until the authorized
response arrives; previews contain no interactive records. Account controls use
the already resolved session rather than waiting for public score data. Changed
profile data rebinds an open receipt dialog's return target by submission identity.

A session change restarts interrupted People reads; unchanged polling does not.
A failed next-page read preserves the earlier rows and retries the same offset.
Permission failures still remove the stale view. These paths retain account,
request and cache-generation checks.

Notebook continuity
-------------------

Admitted browsing now starts a bounded optional queue after the selected page
can paint. It prepares Timeline, the complete note-summary index, current scheme
details/graph data, the viewer's profile, map assets, the first People page and
latest submissions. Foreground reads, open dialogs, issuance/submission, hidden
tabs and Save-Data pause that queue. Its JSON jobs run serially; one next-page
preparation or explicit user intent can overlap, and fixed script groups can
load concurrently. It stops scheduling after 24 jobs or 4 MiB of decoded
response accounting per account/read epoch; the final response can cross the
byte threshold. Failures leave the normal foreground fallback available.
No challenge is generated and no hidden graph/list is rendered by warmup.
Only the eight current releases are prepared automatically; archived details
require navigation or intent. Those current details total about 2.32 MB decoded
and 132 KB gzip in the measured catalogue, including explanatory material.

The browser-only index projection is all-or-nothing: at most 500 visible notes
and 512 KiB encoded. It preserves the same latest-visible revision, ownership,
publication, proposal and scope rules as the paginated endpoint. Overflow returns
no partial list and the UI uses ordinary server pagination. It excludes bodies
and imported private metadata. Complete indexes let categories, exact tags and
pages change locally; text searches keep the existing server Unicode/search
semantics. Trash and reviewer views always use their authoritative endpoints.

The index lives in bounded account/session memory. A Notes entry after ten seconds
can refresh it quietly without disabling local filtering/pagination. Full expiry,
writes, session changes and permission loss retain their invalidation rules.
Core index/Timeline entries take eviction priority over individual bodies while
still sharing the existing serialized-size/five-minute cache bounds. Server-paginated lists
can prepare one next page; expanding a summary can prepare its full note.
Curated bodies and citation pins appear before secondary request-status reads;
pending status actions remain disabled and only that pane updates afterward.

The paragraphs below describe retained server-query fallback behavior and the
earlier continuity measurements; they do not claim local filtering for text search
or an incomplete index.

Changing a notes filter retains the previous nonempty, admitted list while the
new server query runs. Those rows are a previous view, not a locally computed
answer: pagination and mutation controls wait for the fresh result. Empty states
are shown only for their matching query. Exact cached query pages can paint
immediately. Search wording is fixed before the first response, and replacement
rows receive focus only when the departing rows still owned it. Notes search
remains server-side across the full visible collection, not just the loaded page.

Timeline uses the existing bounded account/session read cache (12 entries,
two million serialized JSON characters total, five-minute TTL). A warm visit paints its cached aggregate and still
requests fresh data; an unchanged result preserves the existing SVG. Revocation,
account/CSRF changes and writes retain their existing invalidation rules. No
private note bodies, account permissions or server-side sessions are cached by
this change, and no browser persistence was introduced.

Once a Timeline or note-body prefetch is consumed, only its selected-view request
may save that result. An older intent cannot overwrite a newer same-key cached
read after leaving and returning to the page. Reverse-completion tests cover both
cases; the existing cache limits and account/permission invalidation still apply.

Controlled Chrome comparison at 200 ms simulated RTT / 10 Mbps, using isolated
synthetic accounts: warm Timeline became visible at a median 15 ms rather than
214 ms; its fresh response still arrived around 213 ms. A changed notes filter
kept prior rows visible at 15 ms instead of leaving a blank list until 231 ms;
fresh requested results arrived around 212 ms. These are continuity measurements,
not hosted latency guarantees or evidence that cached rows answer a new filter.

Authored-note summaries join publication, withdrawal and active deletion status
in their existing page query, omitting unused import provenance and status reason
columns. Uniqueness constraints keep these joins one-to-one. An isolated owner
or reader overview fell from eight SELECTs to five, with identical summary data;
an all-curated page already used three. Hosted beta admission adds its separate
fresh access check. Bodies, complete revision history and durable export data
remain unchanged. Tests cover visibility, status, repeated deletion/restoration,
pagination, SQL shape and omission of private bodies from summary responses.

Brand decoding and interrupted responses
---------------------------------------

The same logo artwork now uses a 17,875-byte derivative instead of 421,760 bytes,
large enough for the header at 3x pixel density. Its existing frame reserves space;
an incomplete image becomes visible only after decoding, with no reveal animation.
Already complete images are not re-hidden if bootstrap arrives late. Main CSS
now arrives inside the HTML document, with its exact hash allowed by that same
immutable asset's CSP. This removes a render-blocking request and the separate
stylesheet-failure window. Bootstrap now also arrives inline under its exact
script hash, selecting the public frame before body parsing and overlapping the
fresh session read with remaining downloads. It and all deferred scripts remain
ahead of the embedded style so its bytes do not delay their discovery. The small initial
canvas style remains. See first-paint-packaging.txt for representation/cache
rules and logo-delivery.txt for artwork provenance. A white canvas before the
document arrives is not under the page's control; a hosted cause for the earlier
reported flash has not been established.

API errors distinguish a response body interrupted after headers from malformed
JSON and an unexpected HTML service page. Deadlines and explicit retry remain;
requests, especially writes, are never automatically replayed by this handling.
Synthetic Chrome streams reproduce each classification. This does not establish
which condition caused a particular hosted error after repeated reloads.

Remaining architectural limit: during a rolling deployment, a cache miss for an
old ?v= asset URL can reach a newer process and receive its current bytes with
revalidation required. No CSP/304 mismatch was found. Exact version retention
would require a deliberate asset publication design; rejecting old URLs would
break in-flight pages and is not a suitable quick fix. No such serving change
is included in this checkpoint.

Metadata SQL
------------

Startup prepares one immutable compact scheme index and its catalogue revision.
The revision remains the SHA256 of the same canonical complete catalogue. Each
request receives independent mutable copies of its small label metadata, then
fresh recovery/participant SQL. These server metadata caches never retain account
permissions, scores or receipts.

Scoring and milestones join the same trusted profile tuples through a typed,
materialized JSON relation. This replaces thousands of individual VALUES bind
parameters that prevented SQLAlchemy compilation caching. SQLite uses json_each;
PostgreSQL17 uses jsonb_to_recordset with explicit column types. Materialization
keeps JSON extraction outside the per-receipt join. Score weights, validation of
the original receipt tier's JSON type, ordering and all ranking windows remain
unchanged. The database schema is unchanged.

The release contract pins the reviewed scoring.py query implementation to its
new exact hash; it is not added to the ordinary mutable-file list. This specific
change replaces the metadata relation only, with old/new query parity required
on actual PostgreSQL 17 before CI passes. Scoring policy/constants and native
runtime, dependency and schema pins remain unchanged.

Checks:
- tests/test_read_performance.py and test_scheme_projections.py verify the full
  catalogue fingerprint, all32 release/1466 profile labels, mutation isolation,
  provider invalidation and fresh progress.
- tests/test_metadata_relations.py compares actual typed rows and scoring /
  milestone query outputs to the original VALUES implementation. Cases include
  strings/booleans/floats/null or forged tiers, late/incorrect receipts, named
  parameter sets, inheriting/non-inheriting releases and new live results.
- The required metadata-postgresql CI job runs those tests against both SQLite
  and the digest-pinned official PostgreSQL17 service. Its database address and
  synthetic credentials are fixed to loopback; each PG test uses a new schema in
  a rolled-back transaction. No hosted settings or databases are read.

Local SQLite-only check:
  python -m pytest -q tests/test_metadata_relations.py -k sqlite

CRUCIBLE_METADATA_POSTGRES=1 enables only the fixed disposable CI connection
defined in that test file; it is not an arbitrary database URL override. A local
run with PG tests skipped does not certify PostgreSQL behavior. Existing broader
scoring, people and milestone tests remain necessary; no performance benchmark
is a correctness replacement or a hosted latency guarantee.
