Read-path preparation and metadata SQL

Browser loading and small projections
------------------------------------
The notebook's scheme map renders from its bundled graph without waiting for
the complete profile catalogue or live recovery aggregates. Its action links
use GET /api/schemes?projection=map, a small current-release identity list with
the normal fresh beta admission check. A slow link-index read does not hide the
graph. Opening a scheme can finish/retry that shared read without replacing a
research-note popup or moving focus away from an existing link.

The browser requests summary=true on challenge GET/POST. These responses carry
the same instance identity, deadline, submission status, output length and
download link, without transferring public-key/ciphertext bytes. Default API
responses and exact challenge downloads retain the complete original inputs.
Existing-instance GETs join the submission in the instance query and do not
repeat the already-proven round lookup (three member-read SQL statements,
including both fresh access checks, instead of five).
Summary reads also omit the public-input JSON column from the database query,
including reuse of an already issued instance. Query-scoped raiseload prevents
an accidental property access from silently fetching that large column later.
Output length comes from the instance's stored manifest, which already governs
answer validation. Missing or invalid historical declarations remain readable
with unknown length; full API responses and downloads preserve their inputs.
Generation, ownership, scope, parameter and admission policies are unchanged. Visiting
an exact challenge route starts its read-only status request alongside scheme
descriptions, then consumes that result once. It never speculatively generates.
Previously authorized instance summaries can paint an exact same-round revisit
from bounded session memory while their status revalidates. Instance actions
wait for the fresh read. Rotation, revocation, writes and hour/selection changes
invalidate or separate these views; a failed refresh removes the saved summary.

Database pool checkout exhaustion returns 503 and Retry-After: 2 from both
outer admission and application handlers, with no connection/credential details.
The existing connection cap and checkout timeout remain unchanged. This is a
controlled overload response, not additional capacity or a hosted load-test claim.

tests/test_loading_projections.py covers exact full-download preservation,
small responses, fresh membership, map SQL budget and real pool exhaustion /
recovery. Standalone frontend and Chromium checks hold independent responses
to verify overlap, route/session ownership and an unblocked graph. Timing is
not asserted against a fast local server. Hosted signed-in latency and provider
CPU/database placement still need separate measurement.

Public-site observation, 24 October 2026: three fresh-connection anonymous
/api/session requests took 249–294 ms, while Server-Timing reported 19.85–28.64 ms
inside the application. The no-database /health/live path took 239–347 ms. The
difference includes network/proxy overhead; this is a small developer-machine
sample, not a signed-in challenge or capacity benchmark. Reducing sequential
requests matters even when an individual handler is fast.

Loading presentation
--------------------

Cold catalogue reads reserve the heading and four-column table layout using
neutral placeholders. Heading fonts and spacing match the populated catalogue;
there is no pulsing, stagger or artificial minimum display time. Private scheme
and participant data still wait for fresh session admission. Warm reads retain
the current content when the existing cache policy permits it.

Transient read statuses are visually hidden but remain accessible to assistive
technology. Errors, retry controls, real empty states and submission feedback
stay visible. This is presentation continuity, not a reduction in network time.
Held-response browser checks compare typography and geometry at desktop and
mobile widths; ownership tests cover navigation, access loss and late responses.

Metadata SQL
------------

Startup prepares one immutable compact scheme index and its catalogue revision.
The revision remains the SHA256 of the same canonical complete catalogue. Each
request receives independent mutable copies of its small label metadata, then
fresh recovery/participant SQL. These server metadata caches never retain account
permissions, scores or receipts.

Scoring and milestones join the same trusted profile tuples through a typed,
materialized JSON relation. This replaces thousands of individual VALUES bind
parameters that prevented SQLAlchemy compilation caching. SQLite uses json_each;
PostgreSQL17 uses jsonb_to_recordset with explicit column types. Materialization
keeps JSON extraction outside the per-receipt join. Score weights, validation of
the original receipt tier's JSON type, ordering and all ranking windows remain
unchanged. The database schema is unchanged.

The release contract pins the reviewed scoring.py query implementation to its
new exact hash; it is not added to the ordinary mutable-file list. This specific
change replaces the metadata relation only, with old/new query parity required
on actual PostgreSQL 17 before CI passes. Scoring policy/constants and native
runtime, dependency and schema pins remain unchanged.

Checks:
- tests/test_read_performance.py and test_scheme_projections.py verify the full
  catalogue fingerprint, all32 release/1466 profile labels, mutation isolation,
  provider invalidation and fresh progress.
- tests/test_metadata_relations.py compares actual typed rows and scoring /
  milestone query outputs to the original VALUES implementation. Cases include
  strings/booleans/floats/null or forged tiers, late/incorrect receipts, named
  parameter sets, inheriting/non-inheriting releases and new live results.
- The required metadata-postgresql CI job runs those tests against both SQLite
  and the digest-pinned official PostgreSQL17 service. Its database address and
  synthetic credentials are fixed to loopback; each PG test uses a new schema in
  a rolled-back transaction. No hosted settings or databases are read.

Local SQLite-only check:
  python -m pytest -q tests/test_metadata_relations.py -k sqlite

CRUCIBLE_METADATA_POSTGRES=1 enables only the fixed disposable CI connection
defined in that test file; it is not an arbitrary database URL override. A local
run with PG tests skipped does not certify PostgreSQL behavior. Existing broader
scoring, people and milestone tests remain necessary; no performance benchmark
is a correctness replacement or a hosted latency guarantee.
