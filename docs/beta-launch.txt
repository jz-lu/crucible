Identity implementation prepared 18 October:
GitHub is the primary sign-in when configured, with existing password sign-in
available as a fallback. The user registered the hosted OAuth app on 22 October
with the canonical callback and token expiration enabled. Provider credentials
are not installed in the hosted environment; the feature remains disabled in the

Keep stable Crucible UUIDs. Existing-account linking requires a signed-in browser
and fresh password confirmation; there is no merge by matching email or handle.
GitHub numerical IDs identify provider accounts. OAuth uses state, browser binding
and PKCE; requests no repository scope; stores no provider access token. Provider
login does not confer beta membership. Existing mailbox-bound invitations and
reviewer/admin roles remain separate. Agent access still uses scoped Crucible
tokens, never GitHub credentials.

Password reset is available only through an already verified mailbox. Links are
short-lived, one-use and tied to the current credentials; reset revokes browser
and agent sessions while preserving contributions and linked identities. Delivery
uses a bounded background task, not a durable queue: a process restart can lose
that email and the user may request again. Unknown/unverified/provider-only
accounts get the same request response. Mail must be configured before enabling
recovery. Real GitHub authorization and real SMTP delivery still need end-to-end
verification with operator-provided credentials; fixture tests do not replace it.

Start with 5–10 invited testers as the recommended first cohort, then measure
before expanding. This is a rollout recommendation, not a measured capacity
claim or a replacement for any later 100–150 participant target.

DEVELOPMENT AND RELEASES

Local development keeps its own database and secret. The hosted database becomes
authoritative for beta contributions after cutover. Never run experimental local
code against the beta database. Do not automatically synchronize databases or
overwrite beta records with a developer snapshot after initial migration.

Before building a release, checkpoint the complete intended source tree. The
earlier research pipeline is checkpointed at 3e96b26; this beta preparation is
additional work that must also be included in the intended release. Deploying
only that Git HEAD would omit these additions. Avoid including credentials,
.local data, test outboxes,
private notes or unreviewed build outputs in the checkpoint/image.

Release procedure to rehearse on the target host:
1. Build from an exact checkpoint and freeze its dependencies, Python patch
   version, toolchain, trusted native artifacts and their review evidence.
2. Run portable and native tests, then PostgreSQL integration tests against a
   disposable isolated database. Do not present mocks or SQLite as PG execution.
3. Back up beta before migrations; rehearse schema compatibility and restoration.
   Apply schema changes as an explicit release step, not on every process restart.
4. Promote the tested application release. Keep one app process initially because
   generation and password-work capacity limits are process-local.
5. Verify health, sign-in, browser/agent challenge submission and publication.
   Keep the prior application artifact. Reverting application code must not wipe
   new participant data; incompatible schema rollback requires a recovery plan.

Fallback host assets: deploy/crucible.service and deploy/Caddyfile.example prepare unprivileged
loopback hosting behind HTTPS with automatic restart and bounded logs.
docs/beta-host.txt documents explicit deployment and encrypted backup/restore. Trust forwarded client addresses
only from the actual local proxy; never trust arbitrary internet headers. Use a
dedicated database role, verified TLS and restricted database network access.
Credentials belong in protected runtime configuration, not Git or CLI arguments.
Submitted attack/proposal code remains inert evidence, never server-executed.

NATIVE PORTABILITY: REQUIRED BEFORE FULL-CATALOGUE HOSTING

The current Mac installation validates 32 registered adapter releases. That is
local artifact integrity evidence, not Linux execution evidence. Several workers
and cryptography's native extension have Mac-specific hard pins. Some builders
also pin Mac static dependencies. Startup currently validates archived adapters
as well as current ones, so reducing the beta issuance allowlist alone does not
remove the need for their runtime artifacts.

AdapterVersion retains the original source/artifact pair per (scheme_id,
version). A Linux rebuild has a different identity; even a Python patch-version
change can alter some artifact identities. The additive implementation_builds
ledger records explicitly reviewed alternatives without replacing that baseline.
Do not delete old pins, rewrite receipts, edit digests to match whatever is
installed, or weaken verification to make a host start.

Build admission requires an existing release baseline, an exact manifest digest,
an operator identity and review rationale, and retained build/evidence identities.
This is an audit mechanism, not an automatic proof of equivalence. No Linux
build has been admitted. Changed constructions still require new scheme versions.
Do not alter stage parameters or scores merely to port the runtime. See
docs/linux-runtime-build.txt for the isolated build procedure.

For the first beta, rebuilding the complete registered inventory is less invasive
than redesigning archived-generator loading. Build/runtime directories must be
separate from account data, including HQC's currently .local-based output path.
Linux known-answer vectors, codec/equivalence checks, honest agreement, resource
limits and the full backend suite need a real Linux runner before acceptance.
Existing Mac benchmark reports retain their original machine/artifact identity;
Linux must not silently inherit or relabel those measurements.

DATA TRANSFER AND RECOVERY

scripts/beta_transfer.py now implements the initial SQLite-to-PostgreSQL copy;
docs/beta-transfer.txt gives its command, cutover procedure and validation scope.
The synthetic Linux/PostgreSQL 17 rehearsal passed all 21 transfer tests,
including seven real PostgreSQL integration tests across all 41 schema tables
at the 0020 preparation checkpoint. The later login pass repeats transfer and
restore coverage at head 0022, including the three new authentication tables.
One check creates an actual pg_dump archive, restores into a second fresh
database, and compares every table's count and typed digest. This does not
validate DigitalOcean managed backups or a recovery on the eventual beta host.
The tool requires a consistent read-only source snapshot, matching schema heads, an empty
destination and complete table inventory. Copy in foreign-key order within a
destination transaction. Preserve UUIDs, password hashes, timestamps, JSON values,
text, revision/content hashes, source bundles, reviews and historical flags.
Compare row counts and stable per-table digests, not just account/note totals.
Test large JSON integers, Unicode, whitespace, nulls and immutable revision links.
Notebook export/import is participant portability, not a whole-service backup.

The original secret is part of the recovery set: stored answer MACs and replay
checks depend on it. Back up the database, secret, source/native release manifest
and role configuration through appropriately restricted channels. Do not print
or commit their contents. Do not generate a replacement key over migrated data.

For final cutover, pause source writes briefly, take a consistent final snapshot,
transfer and verify it, then open beta access. Preserve the original recovery set
privately. Move routine local development to synthetic data and a separate key;
avoid leaving active beta credentials in day-to-day development. Accounts and
passwords can survive while users sign in and connect their agents afresh. Any
session/token invalidation must be explicit and recorded, not an incidental loss.

Migration does not enroll every old account. Grant the intended beta participants
explicit membership, configure reviewer/admin UUIDs separately, and verify their
access. No contribution becomes internet-public through this migration.

Production hides development-only self-review approvals. Existing decided
revisions cannot simply be reviewed again through the current API. The existing
path is an author-created new revision followed by a new publish request and a
different reviewer's approval. Preserve the old revision/decision unchanged; do
not flip test-only flags or invent approval during transfer. Select another human
reviewer before expecting countableclouds's own notes to be community-readable.

Recovery target proposed for the pilot: at most one hour of lost work and restore
within four hours. These are targets to validate, not current service promises.
Verify managed database recovery and encrypted logical backups by restoring to
a separate temporary database and checking content/revision digests and actual
user workflows. VM backups alone cannot meet this requirement. Keep key recovery
possible if the application host is lost.

PREFLIGHT AVAILABLE NOW

deploy/beta.env.example is a deliberately incomplete, secret-free template. The
application does not automatically load it. Supply actual values using the host's
protected process environment. With an explicitly configured production env:

  .venv/bin/python -B -m scripts.beta_preflight
  .venv/bin/python -B -m scripts.beta_preflight --runtime --database

The first command checks configuration without connecting to a database, sending
mail or reading native artifacts. The second opts into trusted native-manifest
inspection and read-only PostgreSQL schema, role-membership and implementation-pin
checks. PostgreSQL requires an explicit network host and sslmode=verify-full.
Use the provider CA for Standard Edition. Connection/statement/lock timeouts and
read-only transactions bound the checks; errors redact credentials. Neither
command generates challenges, changes schema, grants access or repairs mismatches.
Use -B to suppress Python bytecode writes as well.

Reports label unselected checks not_checked and always say deployment_approval:
false. Exit 0 means the selected automated checks passed, not that migration,
email, backups, workload behavior or independent build review has been established.
